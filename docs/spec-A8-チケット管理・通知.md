## 0. 原則

- **「記録も管理も一番」**：シアティ(記録)＋チケコレ(管理)＋LiveSoul(抽選管理)を1テンプレに統合。任意フィールドは**全オンオフ可**（軽く使う人を圧迫しない）。
- **状態・期限＝TicketAttemptのクエリ可能な個別プロパティ**（要対応の抽出・通知スケジュールの源）。名義以外の付帯（枚数/手数料/購入URL）＝表示専用 unitFieldsRaw（A1 §8）。
- **チケット申込＝TicketAttempt（申込1件）として独立**。Visitにチケット状態を直持ちしない。同じ公演にFC先行/カード枠/ぴあ先行/一般など複数申込があり、落選履歴・名義別当選率・通知更新に耐えるため。
- **通知は最初から組み込む**（Mystoriumで後付けが面倒だった教訓・08 §4-2）。`TicketSaleNotificationManager` の型と教訓〔権限リクエスト→理由別 ScheduleResult〕を流用。
- CloudKit互換3条件（全プロパティ既定値／`.unique`なし／リレーション optional）を全モデルに機械適用（§7）。
- チケット単体編集の中央タイトルはシステムゴシック体で表示する。抽選の日付入力は`抽選申込開始 / 抽選申込締切`、先着は`発売開始`とし、どの取得フローの工程かを名称だけで判別できるようにする。工程日時は日付と15ptの時刻を横並びにし、時刻は`00:00〜23:55`の5分刻み単一列ホイールで選ぶ。登録・編集のタグ欄は同じ共通部品と余白規則を使う。

## 1. チケット状態 pipeline

### 1.1 状態（TicketStatus・TicketAttemptの個別プロパティ）

観劇/ライブのチケット取得を、抽選ルートと先着ルートの両方で扱う。画面のProgressは参加体験ではなく取得までに限定する。

```
気になる ─┬─(抽選)→ 申込前 → 当落待ち ─┬→ 当選 → 入金待ち → 取得済み
          │                              └→ 落選
          └─(先着)→ 発売前 ─────────────────→ 取得済み
                                      （見送り＝任意の終端）
```

| 状態キー | 表示名 | 意味 | 要対応か |
|---|---|---|---|
| `interested` | 気になる | 行きたい候補。まだ動いていない | — |
| `beforeApply` | 申込前 | 抽選の申込受付前/受付中・未申込 | ◎（申込締切） |
| `waitingResult` | 当落待ち | 申込済み・結果待ち | ○（当選発表日） |
| `won` | 当選 | 当選（入金前） | — |
| `lost` | 落選 | 落選（終端 or リセール探索へ） | — |
| `waitingPayment` | 入金待ち | 当選・入金期限内 | ◎（入金締切） |
| `waitingIssue` | 取得処理中 | 旧データ互換。入金後、取得確定前 | ○（受取開始日がある場合） |
| `issued` | 取得済み | 当選・購入・招待等で参加権を取得済み | 参加日未定なら日程入力 |
| `attended` | 参戦済 | 参加完了（記録が主役に切替） | — |
| `skipped` | 見送り | 申込せず/行けなかった（終端・統計から除外可） | — |

- **要対応◎＝落とすと致命（申込・入金の締切）**：ライブラリ要対応ストリップ（spec-B1 §2）の赤系、通知は既定ON。
- **要対応○＝逃すと機会損失（発表・任意のチケット受取開始）**：黄系、通知は既定ON（オフ可）。
- 状態は手動更新が基本。OCR取込・当選日/入金日の経過で候補提示（自動確定はしない・A7原則）。
- 落選/見送りは**統計に含めるか選べる**（応募履歴として残す＝当選率算出に使う／無かったことにする＝除外）。
- 観劇画面の`チケット管理`内に出す進捗は抽選=`申込 → 当落 → 入金 → 取得`、先着=`発売 → 取得`を基本とし、不要な当落・入金は省く。先着の`発売`ノードは`saleStart`を表示し、通知も同日時を`発売開始`として扱う。`購入`は発売後に利用者が行う状態更新操作であり、日付付き工程名には使わない。`発券`と`観劇`は固定ノードにしない。
- 紙発券や電子チケット受取開始が必要な販売サービスだけ、`issueStart`を任意の`チケット受取開始`として`Ticket Schedule`へ表示する。
- チケットスケジュールは参加日未定でも作成できる。`Plan.planKindKey=ticketUndated`の間はComing Upとカレンダーへ出さず、取得後も`参加日を設定`をHomeと観劇のチケット管理に残す。日時確定後はComing Upへ移し、同カード内へProgressを合体する。

### 1.2 申込枠・販売方法（entryRoute・個別プロパティ）

LiveSoul/チケコレ準拠。当選率を区分別に出せる（A5）。

- 抽選の申込枠: `fanClub`（FC先行）/ `official`（公式先行）/ `lottery`（プレイガイド先行、旧キーを継続利用）/ `card`（カード枠）/ `generalLottery`（一般抽選）/ `other`
- 発売待ちの販売方法: `presale`（先行販売（先着））/ `general`（一般発売）/ `resale`（リセール）/ `other`
- 取得済みでは申込枠・販売方法・名義を標準表示しない。抽選から状態を進めた既存値は削除せず、統計と履歴のため保持する。

- 特典付き先行など（LiveSoul の「特典付きオフィシャル先行」）は entryRoute＋任意メモで表現（enumを増やしすぎない）。

### 1.3 期限フィールド（Date?・個別・通知とカレンダーの源）

| フィールド | 用途 | 通知 |
|---|---|---|
| `saleStart`（発売/受付開始日時） | 先着・受付開始 | 発売リマインド |
| `applyDeadline`（申込締切） | 抽選申込 | ◎締切前 |
| `resultDate`（当落発表日） | 結果確認 | ○当日 |
| `paymentDeadline`（入金締切） | 入金 | ◎締切前 |
| `issueStart`（チケット受取開始・任意） | 紙発券/電子受取等が必要な場合だけ | ○開始日 |
| （公演日時＝Performance.date/Visit.date/開演＝U3） | 参戦 | 前日・カウントダウン |

## 2. 通知・リマインダー（v1・UserNotifications）

### 2.1 通知タイプ

| 通知 | トリガ源 | 既定 |
|---|---|---|
| 発売リマインド（通知名=`発売開始`） | `saleStart` | ON |
| 申込締切前 | `applyDeadline` | ON |
| 当落発表 | `resultDate` | ON |
| 入金締切前 | `paymentDeadline` | ON |
| チケット受取開始（任意） | `issueStart` | ON |
| 公演前日 | Visit.date | ON |
| 公演準備期限 | `PlanPreparationTask.dueAt` | ON（期限付き項目のみ） |
| カウントダウン節目（任意：7日前/前日/当日） | Visit.date | OFF開始 |
| 入場準備確認 | 日時確定済みPlanの開始2日前 | アプリ内で必須確認 |

開始2日前以降に未確認のチケット対象Planがある場合、Home表示時に`入場の準備はできていますか？`を閉じられないシートで出す。選択肢は`準備できている`と`あとで確認`だけとする。チケット不要も「当日入場できる状態」なら準備済みに含む。`あとで確認`は翌日9時まで保留する。これは取得後の直前確認なので、取得までの次アクションだけを扱うHomeのTicket Scheduleには混在させない。

チケット管理ページのタイトルは`チケット管理`とする。入口ジャンルの背景色や端末のダーク設定は引き継がず、常にライト基調で表示する。上部に画面内検索、件数付きの`すべて / 要対応 / 進行中 / 取得済み / 終了 / 非表示`状態チップ、チケットが存在するジャンルだけを動的に並べるジャンルチップを置き、既定は`要対応 × すべて`とする。状態フィルターの変更時は、`すべて`を申込まとめ、`要対応`を入力不足または次対応、`進行中`を現在工程、`取得済み`を参加日確定状況、`終了`を終端状態、`非表示`を非表示項目でSection分けする。各申込は独立した角丸カードとし、上段はHomeの`Ticket Schedule`と同じ`現在工程・アイキャッチ / 期限・残日数 / 申込枠・購入先・公演名・参加日時`の情報順、その下に日付付きの全工程Progress、最下段に`次にやること`と具体操作・期限日時を置く。次操作がない終端状態は下段を`現在の状態`とし、期限欄も`期限を入力`ではなく現在状態と`—`を表示する。カード左右には本体と同じ高さの緑・赤の背面角丸カードを数ptずらして見せ、右スワイプは緑の次状態、左スワイプは赤の落選/見送りと編集へ対応させる。VoiceOverでも同じ操作方向を案内する。取得済み・参加日未定は要対応へ残し、参加日設定後にComing Upへ移す。HomeのTicket Scheduleは同じTicketAttemptから現在の対応だけを、期限と残日数・アイキャッチ・先行名・公演名・参加日時を持つカードで表示する。Homeカードと観劇トップの参加日未定Progressカードは、タップで同じクイック操作シートを開く。Homeと観劇トップの見出し右`すべて見る`、観劇Coming Up内の`ほかn件のTicket Progressを見る`は、独立した`NavigationStack`付きシートでこの管理ページを開く。入口ごとの状態・ジャンル・公演文脈引継ぎは次段階で接続する。

ライト固定の範囲は、Navigation Bar、検索欄、状態・ジャンルフィルター、Section背景、一覧カードまでとする。観劇・LIVE等の親画面がダークEnvironmentを明示していても、`TicketOverviewView`の内側でライトEnvironmentとNavigation Barのlight schemeを再指定する。追加・編集等の遷移先は各画面自身の配色仕様へ従う。

個別チケットのクイック操作シートは`進捗管理`と呼び、初期detentを画面高の66%とする。上部はHome Ticket Scheduleと同じ`申込枠 / チケットサイト → 公演名 → 参加日時`の情報順とする。申込枠はチケット、サイトはSafariのアイコン付き取得方法色チップとし、重複名は1個にまとめる。参加日時はカレンダーアイコン付き12pt Semibold、未定時は警告付きカレンダーとオレンジで表示する。Progressの工程色はHomeと同じ意味色を使い、申込=ワイン、発売=アンバー、当落=パープル、支払=ティール、取得=グリーンとする。画面表示は`支払 / 支払締切 / 支払待ちにする / 支払済み・取得済みにする`とし、内部の`waitingPayment / paymentDeadlineAt / paidAt`は変更しない。完了ノードと完了区間の線は工程固有色、現在ノードは工程固有色の二重枠、未到達ノードと線はグレーとする。Progressの日付は編集可能な工程予定へ限定し、支払は`paymentDeadlineAt`、取得は`issueStartAt`を表示する。状態更新時の実績日時`paidAt / issuedAt`を予定日の代用にせず、工程予定が未入力または削除済みなら`—`とする。Progress、次対応、状態更新、参加日設定、詳細導線を同じ視野へ置き、各操作ボタンは14pt Semibold、ラベル基準高26pt、small controlへ抑える。内容が収まらない場合はシート内だけを縦スクロールする。公演参加日時の右へ鉛筆アイコンを置き、選択中TicketAttemptの申込／発売、当落、入金期限、受取日を日付優先フォームで編集する。保存後はProgressとHome Ticket Scheduleを同時更新する。

Progressを表示する観劇Coming Up、ジャンルトップのチケット進捗、公演詳細のチケット管理には、選択中の申込へ直接進む`日付編集`を置く。申込／発売、当落、入金期限、受取の日付は同じ`TicketAttempt`へ保存し、ProgressとHome Ticket Scheduleが同時に更新される。工程の現在位置は`statusKey`で決める。日付優先編集で未完了工程を未来へ修正し、現在状態がその工程より先へ進んでいる場合だけ必要な位置まで後退させる。`issued / attended`は取得・参加の事実を保持し、日付編集だけでは巻き戻さない。過去工程の日付だけを変更した場合も状態を変更しない。

### 2.2 事前オフセット（ユーザー設定）

- 設定画面には`少なめ / おすすめ / しっかり`のプリセットを置く。`少なめ`は申込締切・入金締切・公演前日/当日、`おすすめ`は少なめ＋当落発表・チケット受取開始・期限付き公演準備、`しっかり`はおすすめ＋申込開始とする。新規利用時はおすすめだが通知全体はOFFを維持する。
- 個別スイッチを変更して3組のどれにも一致しない場合は`カスタム設定`として保持する。FC・会員期限、思い出、月刊・年間Favorecoはチケット頻度とは別設定のためプリセットで変更しない。
- 通知時刻はタイプ別に選べる。申込開始・当落発表・チケット受取開始は`設定時刻どおり / 1時間前 / 前日20時`、申込締切・入金締切は`前日＋1時間前 / 前日のみ / 1時間前のみ`、公演は`前日20時＋当日9時 / 前日20時のみ / 当日9時のみ`、公演準備は`前日20時 / 1時間前 / 期限時刻どおり`とする。既定は順に設定時刻どおり、前日＋1時間前、前日20時＋当日9時、前日20時。
- チケット通知のタイトル先頭には`🔔`を置く。抽選申込の開始・締切は`🔔 抽選申込通知`、当落日は`🔔 当落発表通知`とする。先着の発売開始は`TicketAttempt.entryRouteKey`の販売方法を参照し、`🔔 先行販売通知 / 一般販売通知 / 当日券販売通知 / リセール販売通知`へ分ける。未分類は`🔔 チケット販売通知`とし、本文で対象公演と開始／締切を説明する。
- 通知コピーの版を上げた場合は、アプリ更新後の初回起動で既存の予定・チケット通知を一度だけ取り消して再予約し、すでに登録済みの申込にも新しい文言を反映する。
- プリセットは通知するタイプだけを変更し、利用者が選んだ通知時刻は上書きしない。通知時刻の変更時は対象の予約を再同期し、算出結果が過去になった通知は追加しない。
- 通知は**チケット単位でオフ可**、かつ**タイプ別のグローバル既定**を設定画面に持つ。

### 2.3 実装方針（Mystorium教訓の流用）

- **権限フロー**：初回スケジュール時に `UNUserNotificationCenter` 権限リクエスト。理由別 **ScheduleResult**（`.scheduled` / `.permissionDenied` / `.pastDate`（過去日で不発） / `.noDate`（日付未設定））を返し、UIで**なぜ通知が付かなかったかを可視化**（サイレント失敗を作らない＝Mystoriumの反省）。
- **識別子規約**：`ticket.<ticketAttemptID>.<type>`（再スケジュール時に古い通知を確実に置換／状態遷移で不要な通知をキャンセル）。
- **再スケジュール契機**：期限フィールド編集・状態遷移（例：`won`→支払締切通知を有効化、`issued / attended / lost / skipped`→全通知キャンセル）。状態より前の完了工程は再予約せず、`waitingResult`は当落以降、`won / waitingPayment`は支払以降、`waitingIssue`は取得だけを候補にする。
- **通知タップ**：予定・チケット通知へPlan ID、公演準備通知へPlan IDとTask IDを`userInfo`で付与する。タップ時は対象IDを一時保存してカレンダータブへ切り替え、`PlanDetailView`を開く。公演準備は対象行へスクロールして強調する。通知からの起動直後にSwiftUI/SwiftDataが未準備でもイベントを失わず、対象が読み込まれた時点で消費する。旧予約通知は識別子の`plan.<planID>`または`ticket.<attemptID>`から対象Planを復元する。
- **アプリ内ベル**：申込開始・申込締切・当落・入金締切・チケット受取開始の各行はPlan IDに加えてTicketAttempt IDを保持する。一覧は呼出元ジャンルや端末設定に依存しないライト配色とし、各カードを左右16ptの同一余白で中央配置して、遷移シェブロンもカード内へ含める。タップ時は参加記録作成後でもVisit詳細へ転送せず`PlanDetailView`の予定・チケット内容を開き、対象TicketAttemptまでスクロールしてジャンル色の枠で強調する。観劇済みPlanを含め、この入口から開いた予定詳細は左上の戻る操作と右上メニューを常に表示する。会員期限などPlan／TicketAttemptを持たない行には誤った遷移を付けない。
- **カウントダウン**：通知とは別に、ライブラリ/ホームで次公演までの残り日数を表示（LiveSoul/relight/Tickemo 準拠）。表示は都度算出（保存しない）。
- 過去日・未設定は**通知を作らず要対応にも出さない**（静かに握りつぶさず、編集画面で理由提示）。

## 3. データモデル

### 3.1 TicketAttempt（申込1件・独立モデル）

同じ公演に複数の申込がぶら下がる前提で、申込1件を `TicketAttempt` として持つ。

```text
Performance / Plan
  TicketAttempt: FC先行 / 自分名義 / 当落待ち
  TicketAttempt: カード枠 / 家族名義 / 申込前
  TicketAttempt: ぴあ先行 / 自分名義 / 落選
Visit
  実際に観劇・参戦した回の記録
```

| フィールド | 格納 | 理由 |
|---|---|---|
| status（TicketStatus） | 個別（String key） | 要対応抽出・状態バッジ |
| entryRoute（先行区分） | 個別（String key） | 当選率の区分別集計 |
| saleStart/applyDeadline/resultDate/paymentDeadline/issueStart | 個別（Date?） | 通知・カレンダー期間バー |
| ticketSite（購入先） | 個別（String）＋任意で Account 参照 | フィルタ・当選率の販路別 |
| holderName（名義） | 個別（String）＋任意で Account 参照 | 名義別集計・掛け持ち |
| applicationGroupIDRaw / applicationGroupName | 個別（String、任意） | 同じ日程の別サイト申込、または同じ公演・ツアーの複数日程を総合管理でまとめる |
| price（チケット代） | 個別（U12金額に統合） | 費用集計 |
| quantity（枚数）/ fee（手数料）/ purchaseURL | unitFieldsRaw（表示専用） | 集計不要 |
| seat（座席：ブロック/列/番） | 当選後にTicketAttempt、観劇後にVisitへコピー可 | 座席傾向・会場別 |

`setlist` / 演目 / 感想 / 写真 / グッズは Visit 側。TicketAttemptはあくまで申込・支払い・発券・通知の状態を扱う。

- 利用者向けの名称は`抽選グループ`や`先行・受付グループ`ではなく`申込まとめ`とする。抽選と先着の両方で任意入力でき、先行区分とプレイガイドは各TicketAttemptの属性として分離する。
- 同じ日程へ別サイトから追加する場合は同じ`applicationGroupIDRaw`と`公演名｜M/d 会場`を引き継ぐ。同じ公演・ツアーの別日程へ続けて追加する場合は共通IDを維持し、自動生成名だけ`公演名｜ツアー申込`へ切り替える。利用者が入力した独自名は上書きしない。
- 1回の申込に第1希望・第2希望等がある場合も、`希望申込`という別の上位グループは作らず任意タグとして表現する。
- 総合チケット管理は申込まとめ単位でSection表示し、Coming Upは公演日時を主語に1日程＝1Planを維持する。旧版が先行区分＋プレイガイドから自動生成した見出しは、保存値を破壊せず日程またはツアーの文脈名へ表示補正する。
- `applicationGroupIDRaw / applicationGroupName`は個人CloudKitとJSON schema 14、完全／自動バックアップの対象とし、schema 13以前は空文字へ復元する。

### 3.2 公演準備ミニチェックリスト（Plan単位・任意）

- 宿、交通、休暇、同行者連絡、グッズ準備、発券・座席確認等は申込枠ではなく公演へ行くための準備なので、`TicketAttempt`ではなく`Plan`へ紐づける。
- 観劇・ライブのPlan詳細だけに置く。自動モードではTicketAttemptが申込中、当落待ち、当選、入金待ち、発券待ち、発券済みの間だけ有効にし、申込なしでも手動でONにできる。明示ON/OFFは自動判定より優先する。
- 複数申込は`当選・取得系 > 進行中 > 全件終了`の優先順位で判定する。1件でも当選・取得系があれば当選後候補、当選はなくても1件でも進行中なら申込中候補を表示し、全件が落選・見送り・参加済みになった場合だけ自動停止する。
- 申込中は候補を控えめに表示し、当選・取得後は宿・交通を優先候補として強調する。全件終了時は未追加候補とHome/カレンダー上の準備期限を外すが、追加済み項目は削除せず、手動ONで再確認できる。
- 候補は提示だけ行い、自動作成しない。利用者が必要な項目だけ追加し、自由題名、任意期限、完了、編集、削除を扱う。
- 保存は`Plan.unitFieldsRaw`内の`PlanPreparationFields`構造化JSONとする。新しいSwiftDataモデルを増やさず、PlanのCloudKit同期、JSON／完全／自動バックアップ、削除へ同伴させる。
- 未完了かつ期限付きの項目だけをHome/カレンダーの`次にやること`へ表示する。月は`□`帯、週/日は期限時刻のブロックとして表示し、完了またはリストOFFで外す。期限なしは公演詳細内だけに残す。
- 通知全体と`公演準備の期限`がONの場合、有効な準備リスト内の期限付き・未完了項目を、利用者が選んだ`前日20時 / 1時間前 / 期限時刻どおり`のいずれかで1回通知する。識別子は`plan.<planID>.preparation.<taskID>.reminder`とし、完了、削除、期限変更、通知時刻変更、リストOFF、当落フェーズによる自動停止ではPlan単位の古い予約を取り消して再同期する。準備を追加しただけでは期限なし項目を通知せず、算出した通知日時が過去の場合も予約しない。

### 3.3 FC・チケットアカウント（Account・名義/会員/ログイン管理）★2026-07-08

Cherie Log の「複数名義・掛け持ち管理」に加え、チケットサイト/劇場会員/カード枠も同じ場所で管理する。チケットの名義を**実体（Account）**に紐づけ、有効期限・年会費・ログイン導線を一元管理する。

| プロパティ | 型・既定 | 用途 |
|---|---|---|
| `serviceName` | String="" | FC名/チケットサイト名/劇場会員名 |
| `accountType` | String="" | FC / プレイガイド / 劇場会員 / カード枠 / その他 |
| `siteURL` | String="" | 申込サイト・会員ページURL |
| `loginID` | String="" | ログインID（保存可・コピー可） |
| `email` | String="" | 登録メール |
| `memberNumber` | String="" | 会員番号 |
| `accountName` | String="" | 名義（登録者名。家族名義の掛け持ち等） |
| `membershipRank` | String="" | 会員種別/ランク（例：プレミアム/通常） |
| `expiryDate` | Date?（既定nil） | 有効期限 |
| `annualFee` | Int=0 | 年会費 |
| `renewalNotify` | Bool=false | 更新リマインド有効化 |
| `note` | String="" | 備考 |
| `colorHex` | String="" | 名義識別色（一覧のスッキリ表示） |
| `keychainPasswordRef` | String="" | Keychain参照キー（SwiftData/CloudKitにはパスワード本体を保存しない） |

- **関係**：`TicketAttempt` → `account: Account?`（optional・nullify）。1アカウントに複数申込が紐づく。
- **有効期限アラート**：`expiryDate` −（既定30日/7日）に更新リマインド通知（`renewalNotify`＝ON時）。識別子 `fc.<accountID>.renewal`。**うっかり失効を防ぐ**（Cherie Log の主要価値）。
- **掛け持ち一覧**：Account 一覧を colorHex で色分け表示。各アカウントに紐づく申込/当選率/参戦数・年会費合計を集計（A5）。
- **CloudKit互換**：全既定値・`.unique`なし（serviceName＋memberNumber/loginID の正規化で fetch-first upsert・重複防止／名寄せは A6 準拠）・関係 optional。

### 3.4 認証情報の扱い（セキュリティ方針）

- パスワードを保存する場合、**SwiftData/CloudKitには絶対に保存しない**。iOS Keychainに保存し、SwiftData側は `keychainPasswordRef` のみ持つ。
- パスワードの表示/コピー/編集は Face ID / Touch ID / 端末パスコード認証を必須にする。
- バックアップ/エクスポートにパスワード本体を含めない。iCloud同期ONでもパスワード本体はCloudKit同期対象外。
- v1は自動ログインではなく、`サイトを開く` / `IDコピー` / `パスワードコピー（生体認証）` まで。自動入力やブラウザ拡張的な機能は作らない。
- 端末・OSの制約でKeychain保存が使えない場合は、パスワード未保存で運用できるようにする。

### 3.5 管理場所＝「マイ/設定 > 登録情報・連携」ハブ ★2026-07-07 ユーザー指摘

- **FC/チケットアカウント/名義は個々のTicketAttemptに埋めず、ユーザーの登録情報として一元管理**する。「マイ/設定」内に**登録情報・連携ハブ**を置き、そこで登録・編集 → チケット申込は**選ぶだけ**（1回登録・全TicketAttemptから参照。Cherie Log の一元管理と同型）。
- TicketAccountはサービス名を必須、名義・サイトURLを任意とする。同じサービスの複数名義は`劇団FC｜自分名義 / 劇団FC｜家族名義`のように1名義1アカウントで登録する。名義を管理しない利用者は`劇団FC｜名義未設定`のまま使える。
- 抽選入力の`申込アカウント（任意）`でTicketAccountを選ぶと、`ticketSite`へサービス名、`holderName`へ名義、`purchaseURL`へ登録URLをコピーし、同じAccount参照も保存する。登録URLが空で標準プレイガイド名を解決できる場合だけ共通入口URLで補完する。アカウント未選択時は各値を手入力できる。
- **同ハブに外部連携アカウントも同居**：ユーザーはどのみち iOS に Google/Apple アカウントを入れてカレンダー連携する。**外部カレンダー連携（EventKit＝Apple／iOS上のGoogleアカウント経由のGoogleカレンダー・feasibility §4-3 B / A5 §4）**を同じ「連携」画面に集約し、「アカウントを入れる場所」を1箇所にまとめる。
- ハブの構成（v1）：①FC・チケットアカウント/名義 ②外部カレンダー連携（読み取り） ③（サブスク層）iCloud同期＝Apple ID。
- データ的には Account はトップレベルの SwiftData モデル（TicketAttempt/Visit の下にネストしない）。TicketAttemptからは `account` 参照（optional）。**アカウント削除で記録は無傷**（nullify・§3.2）。
- セキュリティ：ハブのパスワード操作はKeychain＋生体認証（§3.3）。外部カレンダーは**読み取りのみ**（favoreco から書き込まない・feasibility §4-3）。

## 4. OCRスキャン取込（A7連携）

- **主フック＝📷チケット画像スキャン**（TheaterRecords 準拠）：チケット手配フォームの予定情報とチケット情報の間へ`画像からチケット情報を読み取る`を常設する。現行は紙/電子チケット画像を1枚選び、Vision OCRで購入先・購入URL・登録内容に対応する工程日時・金額・座席・枚数を候補化する。新規予定だけは空欄のタイトル・会場・日時も候補にし、既存Planの予定情報は保護する。複数枚一括取込は後続段階で追加する。
- 認識結果は**プレビュー確認→確定**（勝手に確定しない・A7 §3原則）。会場は PlaceMaster 名寄せ、名義は Account 候補提示。
- 副フック＝🔗チケサイト/公演URL（OGP：公演名・キービジュアル）＋📍会場（A7 §2 の観劇/ライブ行と一致）。
- **登録ハードルが競合の最大の不満**（Live Rock レビュー：全手動入力が面倒／既存公演は外部連携で引きたい）。ここを OCR＋URL取込＋会場マスターで潰すのが favoreco の差別化の要。

## 7. CloudKit互換チェック

- TicketAttempt のチケット個別プロパティ：全て既定値（status/entryRoute=""、各Date?=nil、price/fee/quantity=0 or ""）。

### 進捗管理シートの長い公演名

2026-07-30以降、個別の進捗管理シートは、表示中の状態変更・参加日設定・詳細導線を操作数として数え、初期detentを2個以下58%、3個64%、4個以上70%とする。本文上余白8pt・下余白12pt、公演名最大2行・88%までの縮小を使い、操作が少ない時は下部余白を残さず、長いタイトルと4操作の時は全操作を初期表示へ収める。既存の66%固定指定よりこの寸法を優先する。
