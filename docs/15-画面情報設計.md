# Favoreco 画面情報設計

> 2026-07-13確定。画面デザインを作る前の情報階層・画面責務の正本。
> Mystoriumの見た目は流用せず、閲覧/編集分離、対象/体験回分離、Draft保存方式だけを参照する。
> 2026-07-21更新: 下部タブの`記録`は`FAVO`へ変更し、推し専用ではなく人物・場所・作品・体験を含む「自分の好き」から横断して振り返るページとする。本文中の旧`記録`タブ表記より本更新を優先する。

## 1. 基本原則

1. 閲覧画面に編集コントロールを混在させない。閲覧画面には編集への入口だけを置く。
2. `ExperienceEvent`（作品・公演・本・施設などの対象）と `Visit`（その日に体験した記録）を画面上でも分離する。
3. `Plan`（予定）、`TicketAttempt`（申込1件）、`Visit`（体験済み記録）を同じ入力フォームで同格に扱わない。
4. 一覧/サマリーでは厳選情報、詳細では保存情報を原則すべて表示する。
5. 登録/編集はDraftへ入力し、保存時だけモデルへ反映する。キャンセルでは正本を変更しない。
6. 長い入力は必須情報を常設し、補助情報をアコーディオンへ分ける。

装飾付き英語Section見出しは英語タイトルを基準にし、隣接する件数と右側の文字操作を第一ベースラインで揃える。背面の日本語装飾はレイアウト寸法へ含めず、空白を除いた5文字以下だけ各文字間へ半角スペースを入れ、6文字以上は文字間を空けない。表示切替などアイコン主体の操作は見出し行の中央位置を維持する。この規則は`Ticket Management / Performance Log / Productions / Interests / Ticket Progress`等の全ジャンルトップSectionへ共通適用する。

### 観劇トップのTicket ManagementとComing Up

- 上段の大判カードは`Ticket Management`とし、チケット未受取、進行中、参加日未定の予定をまとめる。参加日確定済みだけを上段へ出す従来の`Coming Up`という扱いはしない
- 見出し直後へ管理対象の公演カード総数を`n件`で表示する。初期は各公演内の最も近い次対応期限で並べた1件だけを表示し、期限ありを期限なしより優先する。期限なしは参加日、更新日時で補完する。2件以上は`さらに見る（残りn件）`で同じトップ内へ全件展開し、`閉じる`で1件へ戻す。見出し右の`すべて見る`はチケット管理ページへの入口として維持する
- カード上部の`予定`チップは削除し、未取得申込がある時だけ`チケット未取得`を表示する。各未取得Attemptでは申込枠・購入先行の右側、鉛筆の左へ小型`取得済みにする`を置き、状態表示ではなく更新操作であることを動詞形で示す。カード高を増やさず直接受取済みへ更新し、更新後は当該Progressを`チケット取得済み`表示へ置き換え、金額・座席が空なら既存の任意入力案内を続ける
- `Coming Up`は`Interests`の下へ置くコンパクトな日付行とし、取得済み・参加日確定・開演前・未記録で、未解決Attemptが残らない予定だけを時系列表示する
- 取得済みでも参加日未定なら`Ticket Management`に残す。複数申込のうち未解決Attemptが残る予定も管理側に残し、同じPlanを両Sectionへ重複表示しない

### アイコン体系

- 下部タブ、共通ヘッダー、ジャンル入口・管理、ジャンルトップ、詳細、一覧、登録フォーム、FAVO、カレンダー、統計、設定で使う意味アイコンは、単色の`Phosphor Light`を第一選択とする。
- 固定名・動的名とも`FavorecoIcon`または`FavorecoIconLabel`を通し、検索0件・未登録等の空状態は`FavorecoContentUnavailableView`を使う。既存コードが持つSF Symbol名からPhosphor字形へ解決し、対応がない記号だけSF Symbolsへ自動フォールバックして、画面ごとに別系統のアイコン素材を増やさない。
- Homeの独自空状態も`FavorecoIcon`の28ptを基準とする。PICK UPの気になるはBookmark、FAVORECO REPORTの記録なしはImagesのPhosphor字形を使う。
- 標準`TabView`のアイコンはPhosphor字形をテンプレート画像化して渡し、選択色・非選択色は標準タブバーへ委ねる。文字グリフViewを`tabItem`へ直接渡さない。
- テーマパークはCastle Turret、生き物はPaw Printを使い、美術・博物はPalette、本はBooks、チケットはTicket、通知はBellを基準とする。
- 記録詳細Heroの日付、時刻、タグ、会場、座席、天気も同じLightアイコンを使う。評価の塗り星・半星、選択状態、表示形式切替、戻る・進む・開閉、Apple固有操作、バッジ差そのものが意味を持つ未対応記号はSF Symbolsを維持する。
- 記録詳細のチケット・座席カードは、状態=Ticket、申込=Identification Card、購入元=Compass、座席=Chair、画像OCR=Scan、URL=Link、手入力=Plusを使う。複数チケットでも同じ割り当てを使う。
- 保存済みのジャンル記号は変更せず、表示時の変換で統一する。ライト／ダークとも塗り分けや多色化をせず、各画面の`foregroundStyle`をそのまま適用する。

### 対応OS方針

- 最低対応OSはiOS 18とし、保存・登録・閲覧・バックアップなど主要機能を利用可能にする。
- 主対象とUI品質基準はiOS 26以上とする。設計をiOS 18の見た目や操作へ固定せず、iOS 26で利用できる新しいSwiftUIのナビゲーション、スクロール、視覚効果、アクセシビリティ、パフォーマンス改善を優先する。
- iOS 26専用APIは`#available`で分岐し、iOS 18では情報や主要操作を失わない簡潔なフォールバックを提供する。
- 実機の最終デザイン確認はiOS 26を優先し、iOS 18は互換性、レイアウト崩れ、起動、保存データの確認を中心にする。

## 2. 情報階層

```text
Home（全ジャンル横断）
├─ ジャンルトップ
│  ├─ 対象詳細（ExperienceEvent）
│  │  ├─ 記録詳細（Visit）
│  │  └─ 予定詳細（Plan）
│  │     └─ 申込詳細（TicketAttempt）
│  └─ ジャンル内記録
└─ 全記録一覧
   └─ 記録詳細（Visit）
```

## 3. 画面責務

| 画面 | 主役 | 役割 |
|---|---|---|
| Home | 全体の今・思い出 | 全ジャンルの予定、期限、最近の写真、ジャンル入口を横断表示 |
| ジャンルトップ | 対象ライブラリ | そのジャンルで登録済みの作品・施設・銘柄などを探す |
| 記録一覧 | Visitの時系列 | 全ジャンルまたは選択ジャンルの体験履歴を探す |
| 対象詳細 | ExperienceEvent | 作品・公演・本・施設など、何についての記録かを表示 |
| 記録詳細 | Visit | その日に体験した内容をすべて閲覧 |
| 予定詳細 | Plan | これから参加する日時・会場と申込状況を確認 |
| 登録 | 新しいVisit | 必須情報を短く入力し、必要な補足だけ展開 |
| 編集 | 対象/記録/予定のいずれか | 1画面で1種類の正本だけを変更 |

記録一覧の検索欄直下には、`すべて`と記録が存在するジャンルを並べた横スクロール式チェックボックスを置く。初期状態は`すべて`を選択し、ジャンルを押すと`すべて`を解除してそのジャンルだけへ絞り込む。その後は複数ジャンルを同時選択でき、最後の選択を外した場合は`すべて`へ戻る。その下中央に`詳細検索`ボタンを置き、右上のフィルターアイコンは廃止する。詳細検索はNavigationStack内の独立ページとして開き、`日付・期間 / タグ / 同行者 / 写真有無 / 並び順`を表示する。タグと同行者は記録に保存済みの値だけを2列チェックボックスで提示し、複数選択できる。同一項目内はOR、期間・タグ・同行者・写真・ジャンル間はANDで絞り込む。期間は`すべて / 今月 / 今年 / 期間指定`から選び、期間指定時だけ開始日と終了日を表示する。開始日・終了日は両日を含み、開始日を終了日より後へ変更した場合は終了日も同日に揃える。条件クリアではジャンルを含むすべての条件を初期状態へ戻す。

上部の自由検索はタイトル・シリーズ・会場・メモだけでなく、キャスト、監督、主催、作者などの人物/団体名と役割、タグ、同行者、OCR文字、自由追加項目、座席、場所名・住所を横断する。空白区切りの複数語はAND条件とし、各語が異なる保存項目に存在しても一致扱いにする。

記録一覧の件数右へ、ジャンルトップと同じ3列ギャラリー、2列ミニ詳細、横長バナーの表示切替を置く。3列は保存した対象アイキャッチ比率の画像と`日付｜評価`の1行情報帯、2列は画像・2行タイトル・日付・5段階評価、横長は画像・ジャンル別の体験済み状態・2行タイトル・日付・会場を表示する。一覧画像には各記録へ追加した写真を自動採用せず、対象アイキャッチだけを非同期縮小表示する。対象アイキャッチがない場合はジャンル色＋アイコンではなく、ジャンル別の既定写真を表示する。画像は各対象のアイキャッチ比率を維持した中央aspect fillとし、映画・観劇のポスター、書影、写真系ジャンルを同じ基準で扱う。初期表示は3列9件、2列6件、横長5件とし、`さらにn件`を押すたび同数ずつ追加する。選択した表示は次回も維持し、旧3列/4列/横長の保存値は対応する新表示へ引き継ぐ。予定・チケット入口は記録画面から外し、カレンダー上部のチケットアイコンへ集約する。

## 4. Home

Home / 記録 / カレンダー / 統計のルート画面は、ステータスバー直下に共通の固定ヘッダーを置く。左の画面名は1行で全体を見せ、Homeのブランド名は先頭を大文字にした `Favoreco` とし、34ptのCormorant Garamond Boldで表示する。ブランド色はライト時にアプリアイコン中央のFに合わせた青墨色 `#192735`、ダーク時は可読性を保つ明るい青灰色とする。ほかの画面名は30ptを基準とする。右は22ptの通知ベルと38ptのプロフィールの順とする。2操作はそれぞれ44ptの押下領域を持つが、ピル、カード、外側の共通背景で囲わない。ヘッダーは安全領域内の基準位置から6pt上へ寄せ、下端にテーマ色を薄くした全画面幅1ptの区切り線を置く。iOS 26のToolbar自動装飾でダークモードに黒いコンテナが出るのを避けるため、ルート画面のヘッダーは通常のHStackで描画する。詳細画面の戻るナビゲーションは従来どおりシステムのNavigationBarを使う。

表示順:

1. 共通ヘッダー: Favoreco、通知、プロフィール
2. ジャンル入口: 共通ヘッダー直下のテキストピルによるコンパクトな`1段横スクロール`を基本とする
3. `Ticket Schedule`: 全ジャンルのチケット取得に向けた次の対応を表示。0件ならセクション自体を隠す
4. `PICK UP`: `気になる / 予定 / 記録`をタブ一体型の1パネルへ統合
5. `すべてのジャンルを検索`: PICK UP直下の横断検索入口
6. `FAVORECO REPORT`: `今月 / 今年`をタブで切り替え、写真コラージュと期間集計を表示
7. `GALLERY`: 登録日の新しい順に、記録のアイキャッチを2列タイルで最大6件プレビュー表示

PICK UP直下の`すべてのジャンルを検索`は44pt高の1行入口とし、検索画面で`気になる / 作品・体験 / 予定 / 記録 / 人物・団体 / 場所`を一度に扱う。自由検索は複数語ANDとし、タイトル・シリーズ・メモ・人物名・よみ・別名・役割・会場・住所・タグ・座席等の保存値を横断する。結果上部は`種類`と`ジャンル`の2段チップで絞り込み、ジャンルに属さない人物・場所・未分類は`共通`で扱う。結果タップはUUIDだけを渡し、対象・予定・記録・Inboxの既存詳細、または人物・場所の既存管理詳細へ進む。検索行は軽量スナップショットを使い、SwiftData実体や原寸画像Dataを保持しない。

2026-07-27以降、Ticket Scheduleの残日数は70pt欄の中で桁数別に組む。1〜2桁は`あと`11pt・日数40pt・`日`11pt、3桁は9pt・26pt・9pt、4桁以上は8pt・21pt・8ptとする。日数と単位は横方向を固定して省略記号へ変えない。この指定は後述する旧固定値`あと`14pt・日数38pt・`日`15ptより優先する。

次工程の期限が未入力のカードは、左欄の`期限を入力`だけを赤系の注意色で表示する。参加日未定時の`日程を入力`はエラー用の赤ではなく、参加日未定専用のオレンジで表示する。

Homeの`Ticket Schedule`カード右情報欄は、公演タイトルを基準位置から1pt下へ補正する。参加日時は12pt Semibold、カレンダーは日時確定／参加日未定とも同じPhosphor図形の13ptへ揃え、未定時は図形を変えず文字とアイコンをオレンジで示す。カード高、タイトルと参加日時の3pt間隔、進捗管理シートとチケット管理一覧の状態アイコンは変更しない。

チケット管理は入口ジャンルから独立したライト配色境界とする。総合Home、観劇・LIVE等のダーク系ジャンルトップ、カレンダーのどこから開いても、Navigation Bar、検索欄、状態・ジャンルフィルター、Section背景、一覧カードを同じライト配色で表示する。親画面のダークEnvironmentは管理画面内へ持ち込まず、追加・編集等の遷移先は各画面自身の配色仕様へ従う。

`PICK UP`は初期タブを`予定`とし、最後に選んだタブを端末へ保存する。各タブ内は全ジャンル横断の最新候補を最大10件だけ、全幅ページングで1件ずつ左右スワイプ表示する。`気になる`はExperienceEventの更新日と未整理Inboxの作成日を混ぜて新しい順、`予定`は参加日時が確定した未終了Planと今日以降のVisitを日時の近い順、`記録`は参加済みVisitを記録日の新しい順とする。同じ対象に未来Planがある場合は`予定`を優先し、`気になる`へ重複表示しない。未確定日Ticketは`予定`へ入れずTicket Scheduleへ残す。タブ切替はタップ、カード切替は左右スワイプとし、カード末尾から別タブや別ジャンルへ連続移動させない。ページ位置は`現在 / 件数`（最大`10 / 10`）を表示し、VoiceOverでは`最新N件中n件目`と読む。0件は空状態、1件では`1 / 1`を表示する。タブ列と本文は同じ外枠と背景を共有し、カードをさらに独立した外枠で囲わない。項目がある場合は3タブ・全ジャンルとも左を132pt幅、間隔12pt、右を残り幅とし、カード内側余白を2ptへ揃える。PICK UP内のカード高は214ptとし、左列は上174ptをアイキャッチ、その下へ6ptを空け、下30ptをページ位置へ使う。右欄の公式サイト行と操作列の間にも6ptを追加する。横スワイプ中は、ページ位置の背面へ左カード端から右情報欄直前、画像直下からカード下端までの146×38pt不透明面を固定し、隣カードの操作枠を覆う。ページ文字自体は132×30ptを維持する。右欄の末尾には4ptの安全域を予約し、操作ボタンの枠線を横ページングのクリップ境界へ重ねない。ページ位置はアイキャッチ幅の中央、右側の操作ボタンと同じ行へ置き、独立したフッターは作らない。PICK UPには気になる項目の追加ボタンを置かない。元画像の縦横比は変形させず固定枠内でfit/fillする。

2026-07-27以降、PICK UPの固定画像枠は全ジャンル・全タブでaspect fitだけを使う。元画像の上下左右を切らず全体を表示し、余った領域はジャンル色の弱い背景として残す。予定詳細／記録詳細ボタンは固定110ptではなく右欄の残り幅へ縮め、編集64pt＋間隔6ptと合わせてカード内へ必ず収める。通常カードと詳細画面の画像規則は変更しない。

`FAVORECO REPORT`は`今月 / 今年`のタブ列と本文を同じ外枠へ統合し、現在の月・年に含まれる記録だけを写真コラージュ、記録数、ジャンル数、写真つき件数、最多ジャンルで要約する。期間切替はタップだけとし、左右スワイプはジャンル移動へ渡す。`今月`は無料範囲を想定し、`今年`の有料化は将来判断できる独立した期間境界として保つが、現段階ではHome上でロックしない。

`GALLERY`は`FAVORECO REPORT`の直後へ置き、記録のアイキャッチを登録日の新しい順で2列の高さ違いタイルへ配置する。Home上は最新6件だけをプレビューし、ジャンルと年度は複数選択のチェック式Menuで絞り込む。`詳細検索`は全面ギャラリーを検索欄展開済みで開き、タイトル・シリーズ・主催・会場・住所・メモ・同行者・座席等の複数語AND検索とタグ複数選択を扱う。タグ同士はOR、ジャンル・年度・自由検索とはANDで組み合わせる。プレビュー下のグラブバーはタップまたは上方向スワイプで全面表示を開き、全面表示は初期12件、末尾到達ごとに12件ずつ追加する。タイルから既存の記録詳細へ進む。HomeのSnapshotには原寸画像Dataを持たせず、表示中のタイルだけ`ThumbnailReference`から非同期縮小表示する。

PICK UP項目カードは、通常の予定カード用248pt高を流用せず、内容210pt＋上下2ptの214pt高とする。左列は132pt幅の上174ptをアイキャッチ、その下6ptを間隔、下30ptをページ位置、右情報欄との間隔は12pt、カード内側余白は2ptで固定する。右欄は末尾4ptを操作枠線の安全域として使う。画像は対象アイキャッチだけを非同期縮小表示し、記録へ追加した写真は自動採用しない。対象アイキャッチがない場合も同寸法を維持し、ジャンル色＋アイコンではなくジャンル別の既定写真を表示する。気になるの右欄は`ジャンル / タイトル / 対象メモまたは未整理Inbox本文 / 公開期間 / 会場 / 公式サイト / 詳細を見る`、予定は`ジャンル / タイトル / サブ情報 / 日時 / 会場 / 公式サイト / 予定詳細・編集`、記録は`ジャンル / タイトル / 人物要約 / 日時 / 会場 / 公式サイト / 記録詳細・編集`を表示する。気になるの公開期間はカレンダー、会場はマップピンのアイコンを使い、登録がない対象と未整理Inboxでも行を消さず`ー`を表示する。公式サイト行はSafariアイコン＋`公式サイト`、未設定・無効URLはSafariアイコン＋`ー`とし、URL行だけを外部ブラウザへ接続する。申込・購入URLは表示しない。3タブすべてのタイトルは常に2行分の高さを予約し、3行目以降を末尾省略する。各状態で定義した最後の情報行の直下へ6ptの固定間隔を置いて詳細・編集操作を配置し、それ以外の追加予定のない空スロットや可変余白は作らない。操作ボタンは高さ30pt、予定詳細／記録詳細と編集をともにNoto Sans JP 11pt Semibold、詳細側は残り幅へ収縮、編集幅64pt、ボタン間隔6ptとする。気になるの画像・情報欄・詳細ボタンはUUIDをHome親へ渡し、横ページングカード自身には遷移状態やSwiftData再取得Viewを持たせない。

`次の予定`の表示対象は、未終了の`Plan`に加えて、参加日を今日以降へ変更した`Visit`も含める。日付変更だけで暗黙の`Plan`は新規作成せず、未来日の記録を表示上の予定として扱う。同じ`Visit`に表示対象の`Plan`が紐付いている場合は`Plan`を優先し、二重表示しない。両者を日時順にまとめ、`Plan`からは予定詳細、未来日の`Visit`からは記録詳細へ遷移する。

セクションの`予定一覧`は独立した重複画面を作らず、下部のカレンダータブを`予定一覧`モードで直接開く。カレンダー画面は`カレンダー / 予定一覧`を切り替えられ、予定一覧では今後のPlanを日付順・月単位でグループ表示する。行から予定詳細を開き、要対応がある予定には期限アイコンを付ける。ジャンル絞り込みを許可し、完了済みVisitは通常の予定一覧へ残さない。中止・見送り・アーカイブはフィルターから確認できるようにする。

`Ticket Schedule`は画面幅を使う約106pt高・内側余白8ptの横長カードを縦に積む。カード全面と工程ラベルは`抽選申込=ライトシアン / 販売開始=エアリーブルー / 当落=ローズピンク / 支払=ハニーイエロー / 受取・参加日=ミント`の共通意味色を使い、ラベルは`抽選申込 / チケ発売 / 抽選当落 / チケ支払 / チケ受取`とする。申込区分はブルー文字＋ブルー細枠、販売サイトは中立グレー文字＋グレー細枠、両方とも白〜アイボリー面とし、ベタ塗り白文字は使わない。カードの列幅、期限表示、チケット外形、展開、遷移、期限警告は従来仕様を維持する。

`支払い済み`または`受取済み`へ進んだ時点で、金額・座席のどちらかが未入力なら任意入力の確認を出す。その場でチケット代・手数料・枚数・座席／整理番号の編集へ進むか、`あとで`を選べる。

チケット管理一覧は、HomeのTicket Scheduleから情報の見え方が急に変わらないことを優先する。カード上段を`現在工程・64ptアイキャッチ / 期限・残日数 / 区切り線 / 申込枠・購入先・公演名・参加日時`の共通順とし、上段全体をHomeと同じ現在工程の淡色面にする。管理画面だけその下へ白い日付付き全工程Progressと次対応を追加する。Section見出しと件数も、そのグループを仕分けた現在工程色へ合わせる。管理一覧のProgressは現在工程だけを工程色、完了済みと未来を中立グレーで示し、次に見る場所を1色に絞る。申込枠・販売方法・購入先は共通中立チップとし、期限未入力・超過だけをコーラルの警告色にする。状態フィルターは表示対象だけを絞り、別の小型メニューで`公演ごと / 期限が近い順 / 進捗ごと`を切り替える。初期値は公演ごと。期限順は次対応期限の昇順で期限なしを後ろへ、進捗ごとは抽選申込・当落待ち・入金／支払・受取・終端の順でSection化する。進捗管理から状態を更新した場合はシートを閉じ、同じTicketAttempt IDへスクロールして短時間強調する。更新後に状態フィルターから外れる場合だけ`すべて`へ戻し、検索不一致時だけ検索語を解除する。左右スワイプはネイティブの操作メニューを表示する。

工程色カードはまずチケット管理一覧だけへ適用する。Homeの`Ticket Schedule`と個別`進捗管理`シートは従来配色を維持し、管理一覧の実機確認後に同じ色を展開するか判断する。

管理一覧の確認後、Homeの`Ticket Schedule`にも同じ5工程色を展開する。既存の106pt高、画像・期限・公演情報の列幅と順序は変えない。カード外形だけを角落ちのチケット型とし、期限欄と公演情報欄の境界の上端・下端へ7ptの切り込み、境界線へ3pt間隔の縦ミシン線を置く。申込枠・販売方法・購入先は中立チップとする。個別`進捗管理`シートは対象外とする。

開始工程は青系で統一し、抽選申込をライトシアン、販売開始／チケ発売をエアリーブルーとする。当落はローズピンク、支払はハニーイエロー、取得・参加日はミントを使う。

通常の残日数は「あ」「と」を回転させず縦に積み、その右へ大きな日数と小さな`日`を置く。日数文字とカード枠は同じ緊急色へ連動させ、通常はライトで濃紺、ダークでアイボリーのニュートラル色と細枠、明日は赤系1.5pt枠と弱い赤影、今日は強い赤系1.8pt枠と赤影にする。今日が期限でまだ期限時刻前のカードは、Home表示時およびアプリが再びアクティブになった時にカード最外周の赤いシャドウを約2回強弱させる。赤影が強まる各タイミングにカード全体を最大2.5ptだけ左右へ揺らし、小さく振幅を落としながら中央へ戻して、約2秒以内に静止表示へ戻す。工程・プレイガイド等の内側ラベルには影を波及させず、揺れでカード間隔・タップ領域・ジャンルスワイプ判定を変えない。期限超過・明日以降は動かさず、「視差効果を減らす」が有効なら今日でも明滅と揺れを両方行わない。期限時刻を過ぎたら同日でも`期限超過`へ切り替え、濃赤文字・赤枠・薄い赤のカード全面で示す。

チケット追加機能をHomeの独立メニューとして常設せず、期限や当落など利用者の対応が必要な時だけ`Ticket Schedule`へ表示する。

ジャンル入口は大きなタイルやアイコンを使わず、`Home / 観劇 / 美術展 / ライブ...`の短い名称を明朝体の1段横スクロールで固定表示する。先頭の`Home`は全件一覧ではなく、予定・チケット・最近の記録をジャンル横断でまとめるHomeを意味する。表示設定から旧`ジャンル一覧`ON/OFFを外し、過去の保存値にかかわらずHomeとジャンルトップで同じ`GenreNavigationStrip`を表示する。ジャンル間は細い縦線、選択中はジャンル色の文字＋2pt下線、メニュー下は全幅1pt線とする。ジャンルトップ中央のジャンル名は見出しに限定し、直下メニューと重複する▼、タップ選択、一覧ダイアログは置かない。Homeは`Ticket Schedule`を含む本文全体へ1個だけ方向限定スワイプ認識器を適用し、内部で横ページングを使う`PICK UP`だけを明示的な除外領域にする。方向限定Panは指の移動量が24pt以上になってから判定を開始し、未満の指ぶれは内側カードのタップへ渡す。成立した横PanだけUIKit側で内側カードのタップをキャンセルし、タッチ中の本文へ`.disabled`を掛けない。確定先ジャンルのUUIDはHome親画面の単一`navigationDestination(item:)`へ渡す。左スワイプでは画面上の右隣へ進む`Home → 先頭ジャンル → … → 最終ジャンル → Home`、右スワイプではその逆順に循環する。左右24ptの画面端、`PICK UP`、ジャンルトップHero、内側の横スクロールチップは認識対象外とする。実機でTicket Schedule上の左右スワイプ、PICK UPの横ページング、カードの静止／微小移動タップ、縦スクロールとの干渉、縦線と下線のコントラスト、選択ジャンルの自動中央寄せを確認する。

## 4.1 更新案内

アプリのMarketing Versionが前回確認済みのバージョンと異なる場合、オンボーディング完了後の最初の起動で更新概要をシート表示する。同じバージョンでは繰り返し表示しない。新規インストールではオンボーディング前に現在バージョンを確認済みとして保存し、初回利用を更新案内で遮らない。

更新概要はネット接続なしでも読める短いアプリ内データとし、版番号、見出し、要約、主な変更を表示する。`詳細な更新履歴を見る`は`https://ranoviqo.com/favoreco/`を開く。Web側の掲載先をNotion等へ変える場合はこの固定URLから転送し、アプリ更新を不要にする。設定の`サポート > 更新履歴`では、確認済みを含む全更新履歴をいつでも閲覧できる。

観劇記録フォームの主要情報は`参加日・会場 / 評価 / 鑑賞記録 / 写真 / 感想・感情タグ`の5ブロックへ分ける。評価は日程から、感情タグは日程から、お目当て・注目人物は単独ブロックから外す。鑑賞記録へチケット状態・座席・注目人物をまとめ、感想・感情タグへ感想本文・プリセット感情・自由タグをまとめる。各ブロックは公演登録と同じ独立Section、外側見出し、白い角丸面、48pt以上の行高、共通罫線、app chromeの同じ操作色による文字操作・主要ボタン面・選択背景・ONのToggleを使う。初期状態では参加日・会場だけを開き、ほかは説明と入力状態を残して閉じる。写真ブロックは外側見出しと重複する内側見出しを表示せず、写真件数だけを右寄せする。

テーマパークと自然・いきものは、画面上で`施設 → 1回ごとの記録`の2段だけを見せ、イベントを別管理しない。テーマパークは`Coming Up / 来園予定 → Interests / 気になるパーク → Park Log / 来園記録 → Destinations / 施設情報`、自然・いきものは`Coming Up / 体験予定 → Interests / 気になる施設 → Nature Log / 体験記録 → Places / 施設`の順とする。LogにはVisitを個別表示し、施設カードには同一施設のVisitを集約する。施設詳細の予定・記録は日本語の月日・曜日・時刻を使い、サブタイトルがあればタイトル直下へ表示する。施設詳細と記録詳細のMapは保存座標を優先し、住所・施設名によるApple Maps検索と住所ジオコーダーの2段階で解決し、失敗時は再試行できる。共通Mapを使う予定・記録・施設詳細はジャンルを問わず同じ解決順とする。訪問回数は同じ暦日を1回として数えるため、同じ施設・同じ日に2件へ分けて記録した場合は`来園1回・記録2件`または`訪問1回・記録2件`と表示する。1日の「夜の動物園」と「パンダ観覧」は通常1 Visitのメモと写真キャプションへまとめ、分けたい場合だけ同日2 Visitを許可する。写真キャプションは全写真分類で任意入力でき、記録詳細と完全バックアップへ反映する。

観劇以外の記録詳細本文はジャンルごとの別カードを増やさず、公式情報、会場・地図、メモ、写真・分類写真、人物・団体、チケット・座席、基本情報、詳細項目を共通の開閉カードで構成する。カード面は暗色高コントラスト、本文は明色、操作色はジャンル色を暗色面で読める明度へ補正する。書籍は専用4カードを維持し、場所情報がある場合だけ共通会場Mapを追加する。観劇は専用の予定／記録共通構造を維持する。画面差は表示する項目、順序、初期開閉状態だけで作り、同じ意味の部品をジャンル別に複製しない。

全ジャンルトップのHero／Coming Up／参加記録一覧等から開く予定・参加記録詳細は、暗転したジャンルトップの上へ共通パネルとして重ねる。Heroから本文末尾までを1枚の18pt角丸カードへ収め、観劇はゴールド枠、その他は現在ジャンル色の枠を使う。カード全体を単一の外側ScrollViewで上下に動かし、枠内に固定高の独立スクロール領域は作らない。上へ動かすと枠上辺とHeroが一緒に画面外へ移り、本文末尾では枠下辺が現れる。カード外側の下余白は置かず、固定`編集 / SHARE`バーの直前までカードの表示範囲を連続させる。`⌄ 閉じる`と三点操作はカード外の上部固定操作、`編集 / SHARE`は左右各1/2幅・高さ58ptで画面端まで伸ばすSafe Area内の下部固定操作とする。編集は予定／記録それぞれの既存編集画面へ接続し、共有文にはタイトル・日付・時間・会場・登録済み公式URLを含める。パネル内のタイトルまたは`公演情報を開く`から対象詳細へ進む時は、元のパネルを背面に保持したまま対象UUIDを親の単一`navigationDestination`へ渡し、遷移先で再取得して開く。公開公演詳細の戻る操作は、ジャンルトップではなく保持した直前の予定／記録詳細へ復帰する。Heroを含む外側は通常`VStack`、画面外のMap・写真等を含む本文は`LazyVStack`で遅延生成する。遷移は全体の拡大縮小を使わず、18ptの短い下位置から0.18秒でフェードインする。右スワイプ終了は画面幅の左72%以内から開始でき、右へ80pt以上または予測移動420pt以上、かつ横移動が縦移動の1.35倍を超える時だけ判定して本文の縦スクロールと区別する。表示中は標準Tab Barを退避し、閉じると元のジャンル位置とTab Barを復帰する。

対象情報・予定・個別記録の右上三点は、全ジャンルで共通の画面内アクションパネルを使う。背景はそのジャンル色から黒へ沈むグラデーション、枠・区切り・通常アイコンは暗色上で判読できる補正ジャンル色、本文はアイボリーとし、観劇はワインブラック＋ゴールド、削除・非表示は赤とする。起動ボタンの円と外周にはジャンル色を使い、三点記号は明るいアイボリー固定として同系色でも埋没させない。項目は画面種別と保持データに応じて出し分け、対象情報では編集・代表写真・非表示・全記録削除、予定では編集・チケット・カレンダー・URL・記録・予定削除、個別記録では編集・当該記録削除を扱う。外側タップで閉じ、既存の確認ダイアログと処理へ接続する。パネルは画像やぼかしを持たず、表示中だけ行を生成する。

対象編集では対象名などの基本情報に加えて、対象アイキャッチを追加・変更・解除できる。解除するのは`ExperienceEvent.eyecatchData`だけとし、各記録に保存した写真は削除しない。対象詳細とジャンルトップで使う代表画像の優先順位は、利用者が明示指定した記録写真、対象アイキャッチ、記録写真からの自動候補の順とする。観劇では画面名を`公演情報を編集`、画像欄を`公演ビジュアル`とし、公演名、シリーズ、公演種別、公式情報、キャスト・スタッフの改行テキスト、公演団体をこの対象編集だけで更新する。公演登録の基本情報にも`公演ビジュアル`を常設し、取込アコーディオンを使わずローカル画像を選べる。通常選択は画像だけを更新しOCRを行わない。公演ビジュアルは150×212ptで中央配置し、右上のゴミ箱を押した後に削除確認を出す。写真変更はその下の小型中央ボタンとする。公演登録・公演情報編集・公演地編集・観劇予定・チケット手配の通常入力は、上段左の16pt項目名と下段いっぱいの16pt入力欄を持つ66pt基準行へ統一する。項目名と上枠・区切り線の間に9pt、行下に8ptを確保する。`任意 / 必須`は項目名の隣、プレースホルダーは入力欄内へ置く。プルダウン、日付、時刻、Toggle、数量は同じ二段構成とし、選択値を16ptで右寄せして右端から4pt追加で離す。行間の横罫線は`secondary 46%`で共用し、縦罫線は使わない。公演名はフォーカス時に行高が変わらない1行入力とし、長文は入力中に横スクロールして保存値を省略しない。SNSはX／Instagram／Threadsの3アイコンを横並びにし、タップで各URLの入力シートを開く。保存済みだけカラー、未登録はグレーで表示する。既存のSNS文字列から対象サービスを判別し、判別できないリンクも再保存時に保持する。公演登録のURL取得と画像・OCR取得は実線で区切る。ビジュアル解除は右上ゴミ箱＋確認とし、メモは5行分、座席は通常1行・長文時のみ最大2行を予約する。観劇記録では公演名・シリーズ、日付・時刻・鑑賞方法・会場・住所・評価、チケット状態・座席、金額、感想メモ、公式URL・SNS、OCR原文、人物名、自由感情タグを同じ二段構成にする。写真・人物候補・感情タグ候補のカード/グリッドは既存構造を維持する。保存カードはForm端から左右8pt離して角丸枠を保ち、88pt以上の高さと上下14ptの内側余白を持つ。必須入力完了時は淡いジャンル色の背景・枠・アイコンで活性状態を示す。

公開公演Heroの中央ポスターは対象アイキャッチを最優先とし、未登録時だけ記録写真由来の代表写真を使う。Hero背景は中央ポスターを拡大・ブラーせず、対象編集で選択した劇場背景JPEGをアプリバンドルURLから読み込み、Hero本体の実寸へ全面表示する。薄いワイン色と下方ほど暗いグラデーションを重ね、タイトル、会場、リンク、予定／記録追加の判読性を確保する。公式情報は`公式サイト / チケット / X / Instagram / Threads`を固定順で横並びにし、URLがない項目も位置を詰めずグレーの無効表示とする。公式サイトとチケットは文字付きボタン、SNSはアイコンで表示し、登録済みだけ有効色と外部遷移を持つ。中央ポスターはB判比率の148×209pt・ゴールド二重枠、Heroの最小高は620ptとし、予定／記録追加は横幅が足りない時に縦並びへ切り替える。画面左端からの右スワイプは公開公演ページを閉じ、キャスト横スクロール上の操作はキャスト閲覧を優先する。

公開公演の視覚トーンは、舞台背景、黒へ沈むワインブラック面、0.8ptの細いゴールド枠、アイボリーの明朝見出し＋ゴールドの用途別アイコンを基準とする。本文は`LazyVStack`で遅延生成し、カード間は8ptとして連続した舞台プログラムのように見せる。右上の三点操作はネイティブ`Menu`ではなく同じワインブラック＋金枠の画面内パネルとし、編集・代表写真・非表示・削除を直接開く。対象編集の公演ビジュアルはB判相当の150×212ptへ抑えて中央に置き、画像変更、背景3種、基本情報が同じ初期スクロール範囲で見えるようにする。

観劇の対象編集には`公演団体・関係者`を置き、人物／団体の区分と役割を分けて選ぶ。団体役割は`上演団体 / 主催 / 制作 / 企画 / 招聘・提供`とし、団体マスターで上位団体を設定できる。統計の`観劇・団体別`は公演数と観劇回数を団体UUIDで重複除外し、子団体の実績を親団体にも合算する。観劇回の感情タグは基本情報で複数選択し、記録詳細の感想内へ表示する。観劇回の`お目当て・注目した人`は、名前入力と既存人物サジェストを同じ入口にし、各人物へ`お目当て / 気になった / 刺さった / 尊い`を任意・複数選択できる。見出し説明と人物入力の間は8ptに抑え、人物名入力と印象選択の間は区切り線で分ける。人物候補は汎用設定にかかわらず常時表示し、表示名・よみ・別名で検索する。候補選択または完全一致入力では既存人物マスターを再利用する。既存人物への変更も保存ボタンまでは編集Draftに留め、キャンセル時は保存しない。タグは人物カードに併記し、人物マスターやMY FAVOの属性としては表示しない。記録詳細の登録済み人物カードからは人物UUIDで人物マスター編集へ進み、名前・よみ・写真を後から補完できる。同画面のFAVO設定は明示的な任意操作とし、観劇回への登録だけでは自動作成しない。

観劇記録の`写真・アイキャッチ`はMystoriumの編集画面と同じくフォーム上部に配置する。新規追加、編集、既存公演への回追加の3入口で、説明カードや他の入力ブロックより先に表示する。外側アコーディオンを設けず、回別サムネイル、`設定済み / 未設定`、`変更 / 解除`を常時表示する。選べる思い出写真が0枚の場合は、同じ位置の`写真を追加`からライブラリを開き、追加した最初の写真をアイキャッチにする。写真一覧、撮影、ライブラリ追加は、写真0枚では`写真を追加`、1枚以上では`写真一覧・追加`から開く。名称と操作は12.5〜14ptを基準とし、省略表示より2行化または必要最小限の縮小を優先する。観劇記録にはトップ背景選択を表示しない。解除で写真本体や公開公演の公演ビジュアルは変更しない。

観劇記録フォームの外側Section見出しは共通テーマの`globalTint`を使い、グレーだけで階層を表現しない。公演情報を引き継げることを知らせる導入案内は、`この記録で入力する項目`を小見出しにした淡いテーマ色の情報枠へまとめ、本文を11ptに抑える。

標準記録フォームの展開内容も観劇フォームの行構造に揃える。映像作品の`鑑賞日 / 映画館 / 評価`、OCRの`読み取り原文（任意）`、人物・団体の`人物・団体名 / 役割 / 区分`を区切り線付きの独立行で表示する。人物・団体ユニットの説明は開閉行に1回だけ表示し、展開内で同文を繰り返さない。ジャンル既定のトップ背景はBundle内JPEGを直接読み込んで選択タイルへプレビューする。

この回の印象タグは2列×2行の等幅ボタンで表示し、`お目当て / 気になった / 刺さった / 尊い`はすべて1行に収める。小幅では改行せず、同じボタン幅内で必要な範囲だけ文字を縮小する。

## 7. 記録詳細

観劇済み記録の`チケット・座席`は、見出し右端に他の詳細カードと同じ開閉シェブロンを置く。追加申込は見出しと同じ行に置かず、展開内容の先頭へ横幅いボタンで置く。申込0件は`チケット申込`、1件以上は`別の申込を追加`と表示し、閉じた時はボタンと申込内容を隠す。`次にやること`内には重複するチケット申込ボタンを置かず、進捗更新は次アクション、追加申込は`チケット・座席`に分ける。

2026-08-05以降、観劇済み記録Hero右欄の`日付 / 上演時間 / 観劇スタイル / 会場 / 座席`は14pt Regularとする。評価は15pt、アイコンは17pt、行間は6ptを維持する。観劇予定詳細と他ジャンルの記録詳細は従来の寸法を変更しない。

観劇予定／観劇済みの共通Heroは、カテゴリ用JPEG背景を表示し、下部をワイン色へフェードさせる。Hero直下には12ptの短いワイン色フェードを置き、その後の本文上余白を2ptとして、単色の境目や暗い帯を作らず`作品・公演情報`へつなぐ。左に幅140ptのアイキャッチ、右に15pt Regular・行間6ptの「日付・時間・形式・会場・席・評価」を6行固定で並べ、未入力は行を省略せず `—` とする。観劇済みHeroの情報ブロックはHero高を維持したまま従来位置から15pt上へ寄せる。天気はHero上段の公演年／観劇回数または予定種別の右端へ16pt Regularで置き、日付行とHeroの縦幅を圧迫しない。未取得時は `cloud.sun` と `—`、取得済みの観劇記録では保存済みの天気アイコンと最高／最低気温を表示する。

`Visit`の閲覧専用画面。保存情報を原則すべて表示する。

観劇の表示順:

1. Hero: シリーズ名・観劇回数、タイトル、任意サブタイトル、アイキャッチ、日付＋天気、上演時間、観劇スタイル、会場、座席、評価
2. 作品・公演情報: 初期状態は閉じ、主催等、公式URL、チケットサイト、SNS
3. 会場・地図: 初期状態は閉じ、会場名と住所は常時表示。開くとMapと外部地図導線を表示
4. 次にやること: 初期状態は閉じ、チケット申込・入金／発券・遠征ToDo
5. 写真・コレクション: 初期状態は開き、思い出、グッズ、ノベルティ・特典
6. 感想: 初期状態は開く
7. チケット・座席: 初期状態は閉じ、入力済み座席は常時表示。開くと半券／チケット写真、座席、申込情報、金額を表示
8. 遠征・準備の記録: 初期状態は開き、予定段階から引き継いだ宿泊・交通等の内容と金額を表示・編集
9. 費用: 初期状態は閉じ、合計金額は常時表示
10. キャスト・スタッフ: 初期状態は閉じ、この回の注目人物を丸アイコン＋下段の名前で最大3人＋`ほかn人`表示。開くと公演全体とこの回の注目人物を全件表示
11. OCR・取込結果: 初期状態は閉じる

上部は全ジャンル共通の画像主役型Heroとする。標準ナビゲーションバーは完全に隠し、写真上へ独自の戻るボタンと右上メニューを重ねる。右上メニューはジャンル正規色を面、観劇ではゴールドをアイコンと枠の差し色に使い、独立したヘッダー帯を作らない。写真は上部の高さを制限した帯へ中央基準のaspect fillで配置する。縦長写真は天地を均等に切り、画像比率でHero高を押し広げない。白へのフェードは使わず、元画像の色を残したまま下端だけを該当ジャンルの正規色へ溶かす。ページ全体はジャンル色から深色へ続く暗色基調とし、観劇はワインレッド`#8B2F45`を面、ゴールドを操作と装飾の差し色に使う。明るい写真でもステータス、上部操作、Hero文字が沈まないよう、局所コントラストスクリーンと文字影を使う。対象名は帯の下端と重なる位置に置き、その下へ左アイキャッチ、右へ日付、上演時間、観劇スタイル、会場、座席、評価を置く。日付と時間は別行とし、時計行はアイコンと時刻だけを表示して固定の`上演時間`接頭語は付けない。終演が入力済みなら`12:00–15:00`形式で表示する。対象名は対象詳細へのリンクにする。背景またはアイキャッチとして使った写真は直下の写真一覧で重複させない。写真がない場合はジャンル色グラデーションとジャンルアイコンをフォールバックに使う。

観劇スタイルはタグアイコンと選択値だけをHeroへ表示し、固定の`スタイル`接頭語は付けない。`Visit.unitFieldsRaw`内の`styleNames`へ複数値で保存し、スタイルだけを入力した場合もJSONを保持する。旧記録は空配列として互換読込し、SwiftDataスキーマは増やさない。追加／編集フォームではイマーシブ演劇・大衆演劇を含む主要候補を複数選択でき、候補にない表記もカンマ区切りで入力できる。対象そのものの分類に使う`ExperienceEvent.subTypeKey`や、全ジャンル共通のタグとは分け、今回の観劇回の表示情報として扱う。

Heroは早見として日付、上演時間、観劇スタイル、会場、座席、評価までに限定する。席種は別項目を増やさず、座席へ`S席・1階A列12番`のように一体入力する。座席メモ、購入元、申込経路、券面、手数料は下部の`チケット・座席`へ集約する。TicketAttemptがある場合は当選以降の確保済み申込だけを表示し、落選・見送りは観劇回の詳細と費用へ混ぜない。Visit側のチケット状態は確保済みTicketAttemptがない場合だけ同カードへ表示し、基本情報と重複させない。Heroの座席と下部の座席は早見と詳細という異なる役割を持つため、同じ文字列でも許容する。

Hero直下には`公式情報`カードを常設し、公演の公式URLとSNSを表示する。値がない場合もカードや各欄を消さず`未登録`と示す。SNSは公演登録と対象編集で1行1リンクとして入力し、`ExperienceEvent.unitFieldsRaw`内の`socialLinks`へ複数値で保存する。同じ公演に紐づく各Visit詳細はこの公演情報を参照するため自動反映される。観劇回編集では公式情報を読み取り専用とし、対象へ書き戻さない。旧データは空配列として互換読込し、SwiftDataスキーマは増やさない。その直下へ`会場`カードを置き、会場名、住所、埋め込み地図をまとめる。行き方の説明は置かず、施設名と住所は長押しで選択・コピーでき、その下へカード幅いっぱいの横長Mapを置く。保存座標、PlaceMaster座標を優先し、座標未保存時は住所、会場名＋住所、会場名の順でジオコードする。検索処理は表示中のMapコンテナから開始し、全候補に失敗した場合は読込中のままにせずエラー表示へ切り替える。外部地図はApple MapsまたはGoogle Mapsを選択する。Google Mapsは保存座標を優先し、座標がなければ会場名・住所を公式Universal URLの`query`へ渡す。会場未登録時も空状態カードを残す。

観劇では上記を`作品・公演情報`へ拡張する。主催、企画・制作、運営、協賛は入力済み分だけ1列のラベル＋値で表示し、公式URL、チケットサイト、SNSは値がなくても`未登録`欄を残す。狭い2列組みは使わない。任意サブタイトルは同JSONの`eventSubtitle`へ保存する。その後に期限前の操作を集めた`次にやること`、会場名・住所・地図を置く。参加済み記録の`次にやること`は未完了件数にかかわらず初期状態を閉じ、見出しの件数とシェブロンから手動展開できる。`作品・公演情報`は見出しのシェブロンで折りたためる。

編集とこの記録だけの削除は、全ジャンル共通で右上の`…`へまとめる。削除は確認ダイアログを経由する。

観劇の`キャスト・スタッフ`は1つの折りたたみカードにまとめる。公演全体は公演側の複数行テキストを正本とし、`:`または`：`の前後を`役割｜名前`の行として区切る。形式に合わない行は自由文のまま表示する。この回の`お目当て・注目した人`はVisit側の個別登録とし、写真または人物アイコンの下へ名前を置く。閉じた状態は最大3人＋`ほかn人`の要約だけを表示し、開いた状態は公演全体と注目人物の全件をさらに折りたたまず表示する。注目人物は登録してもMY FAVOへ自動追加しない。独立した`スタッフ・関係者`セクションは表示しない。

写真は`思い出 / チケット / グッズ`の3分類とする。空値・未知値を含む既存写真は思い出として扱い、利用者が編集して明示分類できる。Hero背景は各ジャンルの同梱イメージを既定とし、写真1枚目を自動採用しない。観劇、御朱印、映像作品は各3プリセットを持ち、映像作品は`映像作品 / ドラマ / アニメ`とする。映像作品の3枚は1280×583、中央トリミング、下端フェードを前提にする。編集画面で思い出写真を明示選択した場合はそちらを優先し、組み込み背景へいつでも戻せる。自作ジャンルはジャンル色グラデーション＋自分の写真を使う。アイキャッチに使っていない思い出写真は、1枚だけでも全幅へ広げず、3列の正方形aspect fillグリッドへ整列する。

観劇では4分類目として`ノベルティ・特典`を追加する。保存分類と費用計算ではグッズと特典を区別し、特典は金額・費用合計の対象にしない。一方、詳細表示は`写真・コレクション`1カードへまとめ、その中を`思い出`と`グッズ・ノベルティ・特典`の2まとまりで整列する。思い出・グッズ・特典は同カードの`追加`から写真ライブラリを開いて直接保存でき、カード全体を折りたためる。各画像はMystorium同様に中央aspect fillの正方形へトリミングし、4列・列間6ptで並べる。チケット写真は写真・コレクションへ混ぜず、`チケット・座席`へ表示する。感想も独立カードとして折りたためる。観劇予定／観劇済み詳細の開閉見出しは共通16pt Semiboldへ揃える。会場名と住所は両画面で同じ共通部品を使い、3pt間隔の1要約として表示する。

登録・編集の写真一覧は4列・列間6ptの正方形セルとし、縦長／横長の元画像を中央aspect fillしてセル外をclipする。タップは大判の`写真の情報`を開き、長押しは写真情報編集、思い出写真だけのカバー／トップ背景設定、削除の快速メニュとする。OS標準のメニュとPickerはSF Symbolsまたは文字ラベルを使い、独自フォントの未対応グリフを表示しない。写真情報で分類と付随情報を編集する。Vision OCRは非思い出写真の`文字読み取り（任意）`として初期折りたたみ、OCR本文を画像に紐づけたまま保存する。金額入力はチケット／グッズだけに表示し、本文から見つけた金額は候補として提示し、利用者が選んだ場合だけ画像別金額へ反映する。入力中の新規写真は`PendingPhoto.metadata`、既存写真は`PhotoMetadataDraft`に保持し、記録の保存確定前にSwiftDataモデルを書き換えない。思い出へ戻した写真はOCR本文・金額を保存時に空へ戻す。

費用合計は、確保済み以降の`TicketAttempt`にある券面＋手数料、グッズ写真の確認済み金額、遠征ToDoの確認済み金額を費目別に加算する。チケット写真の金額はTicketAttempt金額が0円の時だけ代替値として使い、両方は足さない。既存の`Visit.amount`は構造化明細がすべて0円の時だけ旧合計として使い、明細がある場合は参考値として保持して加算しない。観劇／ライブの記録詳細には`申込を追加`と`遠征ToDo`を置き、元Planがない過去記録では利用者がこの導線を押した時だけVisitへ紐づくPlanを作る。

遠征ToDoは既存の公演準備リストを拡張し、通常の準備に加えてホテル、新幹線、飛行機、現地交通、その他の遠征を選べる。遠征項目は実際の開始／終了日時、任意期限、費用、OCR原文、完了状態を持つ。画像OCRは原文だけを先に保持し、タイトル、日付、金額、種類は候補を利用者が押した場合だけ反映し、保存前には確定しない。通常準備の金額は費用合計へ入れず、遠征種別だけを遠征費として加算する。

## 8. 一覧・サマリー

一覧カードに出す情報は最大で以下に限定する。

- カバー写真
- タイトル
- ジャンル
- 日付
- 場所
- 評価または現在状態
- メモ1行

人物、金額、OCR、URL、天気は通常一覧に常設しない。期限や未整理など、次の操作に必要な状態だけ補助表示する。

## 9. 思い出の登録

下部タブバーはSwiftUI標準`TabView`を使い、`Home / 記録 / 追加 / カレンダー / 統計`の5項目をシステム標準の寸法で並べる。独自のカプセル、背景色、影、下端余白は追加せず、`.toolbarBackground(.ultraThinMaterial, for: .tabBar)`で透過ブラーを明示する。iOS 26では本文上へ浮く透過ブラーの標準タブバー、iOS 18では従来型の半透明タブバーとして表示する。各タブのルートは下端container Safe Areaを越えて描画し、本文とポスターをバーの背後まで続ける。スクロール末尾にはバー高相当の操作余白を持たせ、最後の要素をバーに隠さない。`追加`は独立画面へ切り替えず、標準タブ項目の選択をBindingで横取りして現在のタブを維持したまま表示する。内容は押した時点の表示中ジャンルUUIDからジャンル別定義を解決して固定する。観劇は専用3入口、Homeとその他ジャンルは通常4入口とし、ジャンル固有メニューを追加する場合も同じ定義へ集約する。Homeの上部ジャンルタップと本文横スワイプは同じジャンル遷移UUIDを正本とし、UUIDが入った時に追加文脈を有効化し、ジャンル画面を閉じてUUIDがnilになった時だけ総合Homeへ戻ったものとして解除する。Viewの`onAppear / onDisappear`は解除判定に使わない。FAVO・カレンダー・統計へ移ってもHomeのジャンル状態は保持し、`追加`押下時に現在の下部タブがHomeなら保持中ジャンル、Home以外なら通常メニューを選ぶ。

Home本文のジャンル横スワイプは縦スクロール用Panとの同時認識だけを許可し、Ticket Scheduleカード等のタップ・長押し操作とは排他にする。横パン成立時はカードの選択状態を破棄し、ジャンル遷移先UUIDが有効な間は開始地点の進捗管理シートを表示しない。短いタップは従来どおりカード操作、縦移動はスクロールとして扱う。

1. `予定を立てる`: これから体験するPlanを登録
2. `体験済みを記録`: 予定を経由しない正式なVisitを直接登録
3. `クイック登録`: 通常と同じExperienceEventを、ジャンル/タイトル必須、アイキャッチ/URL/読み取りメモ/短いメモ任意の簡易フォームで`気になる`として保存
4. `チケットスケジュールを追加`: 対象イベントを検索または最小作成し、そのPlanへ抽選/発売スケジュールを紐付ける

初期状態では`予定を立てる`を既定の追加方法とする。利用者が設定で既定値を変更できるようにしても、入口の並び順自体は動かさない。観劇、ライブ、美術展、おでかけなどは予定起点を基本とし、御朱印、お酒、過去記録の移行などは`体験済みを記録`から直接登録できる。

`予定を立てる`と`体験済みを記録`は対象情報と基本入力部品を共用するが、初期状態を分ける。

| 入口 | 初期表示する情報 | 初期状態で閉じる情報 | 主な表示先 |
|---|---|---|---|
| 予定を立てる | 対象、日時、会場、通知、チケット | 写真、感想、評価 | 次の予定、カレンダー、要対応 |
| 体験済みを記録 | 対象、体験日、写真、感想、評価 | 通知、抽選、発売 | 最近の思い出、記録一覧、統計 |

`予定を立てる`は最初に予定の対象を確定する。主操作は`新しく登録`とし、同じフォーム内でExperienceEventとPlanをまとめて保存する。補助操作の`気になるから選ぶ`では、`気になる`状態の既存ExperienceEventを検索して選び、その対象へ新しいPlanを追加する。検索対象はタイトル、シリーズ、ジャンルとし、文字幅・大文字小文字・空白の差を無視する。選択一覧はSwiftData実体を保持せず、タイトル・ジャンル・シリーズ・アイコン・UUIDの表示用スナップショットを使い、シート終了後にUUIDを親フォームへ反映する。選択一覧と選択後カードのタイトルは15pt基準の1行とし、長文は縮小する。選択後は対象名、ジャンル、公式URLを予定フォームへ引き継ぐ。対象詳細から開いた場合は選択を省略し、表示中のExperienceEventへ直接追加する。

予定日時はアプリ全体で日本語の年月日表示とする。チケット工程日時は日付と15ptの時刻を横並びにし、時刻は`00:00〜23:55`を5分刻みの単一列ホイールで選ぶ。観劇とライブの`体験日程`だけは日付を1件指定し、その下へ同じ日付の`開場 → 開演 → 終了`を時刻のみで並べ、時・分を一体にした10分刻みホイールで選ぶ。開場は初期状態を`--:--`の未設定とし、時刻選択時の初期候補を開演30分前にする。行末の×で未設定へ戻せる。開演を変更した時はそれまでの開演〜終了の長さを維持して終了も同じ差分だけ動かし、終了が開演より前にならないよう補正する。開場設定済みなら開演との時間差を保って同じ差分だけ動かす。同じ日付を越える値は当日内へ収める。映画、美術展、おでかけ、書籍、酒、御朱印などには開場を表示・保存しない。観劇/ライブのPlanを外部カレンダーへ追加または片方向更新する時は、開場が設定済みなら開場、未設定なら開演をカレンダー上の開始時刻とし、終了はPlanの終了時刻を使う。

Planは必ずExperienceEventへ紐付け、Planだけを単独保存しない。予定日時を持たない`気になる`登録はExperienceEventだけで成立するが、利用者自身の候補日または確定日を入力した時点でPlanを作る。開催日・開催期間など対象そのものの日付と、利用者が行く予定日時は区別する。Plan作成後は対象の`気になる`状態を通常状態へ移す。

予定日を迎えたPlanから`記録を残す`を実行した場合は、対象、日時、会場、チケット参照を引き継いでVisit作成を開始する。元のPlanとTicketAttemptは削除せず完了状態として保持し、同じExperienceEventへVisitを紐付ける。

`チケットスケジュールを追加`は`新規イベント / 登録済みイベント`の2入口とし、チケットだけを独立保存しない。新規イベントではExperienceEvent、Plan、TicketAttemptを同じ保存処理内で作成する。登録済みイベントではタイトル、シリーズ、ジャンルからExperienceEventを検索し、そのイベントに未完了Planがあれば紐付け先を選んでTicketAttemptだけを追加する。文字幅・大文字小文字・空白の差は検索時に無視する。

登録済みイベントにPlanがない場合、または同じイベントに別の予定を作る場合は、選択したExperienceEventへPlanとTicketAttemptをまとめて追加する。既存Planを選んだ後は予定名、日時、会場を参照表示とし、チケット保存によってPlanの日時・会場・公式URLを上書きしない。通常は予定詳細から追加し、下部の`追加`タブはイベント詳細まで移動せず登録するための短縮導線として扱う。

登録済みイベントのPlan選択は`追加先予定｜タイトル / 日時 / 会場`を13pt基準の1行メニューで表示し、長文は1行内で縮小する。選択後の基本情報は`ジャンル / タイトル / 日時 / 会場`を12pt・上下7ptのコンパクトな1カードへまとめ、項目名と値を各1行に固定する。取得済みの値は`primary`で表示し、文字どおりの`未設定`だけを補助色にしてプレースホルダーと区別する。チケット情報内の固定`入力内容｜チケットスケジュール`は登録内容と重複するため置かない。登録内容に応じて切り替わる説明は、情報アイコン、`この登録で入力する項目`見出し、淡いアクセント背景を持つ案内カードとして表示し、未入力フォームのプレースホルダーと視覚的に分離する。説明本文は11ptの1行に固定し、小幅時は68%まで縮小して折り返さない。予定情報とチケット情報の間には、既存Planを選択済みでも`画像からチケット情報を読み取る`行を表示する。読取中は同じ行へProgressを表示し、完了後は検出した候補項目を確認ダイアログで示してから反映する。現在の登録内容で非表示の項目と既存Planのタイトル・日時・会場は候補から除外する。文字入力は名義、購入先、購入URL、金額、座席、タグ、メモを含めて上段項目名／下段入力欄の二段構成とする。

抽選フローの日付入力は`抽選申込開始 / 抽選申込締切 / 当落発表 / 入金締切`とし、先着フローの`発売開始`と名称だけで区別できるようにする。チケット単体編集と予定・チケット一括手配で同じ工程名を使用し、日付順エラーも同じ呼称へ揃える。一括手配の工程名は13ptへ抑える。日程未定時の説明は`未定の予定はComing Up・カレンダーに表示されません`へ短縮し、10pt・最大2行で省略せず表示する。

`クイック登録`はPlanやVisitを作らず、通常と同じExperienceEventを`気になる`状態で作る入力項目限定版とする。別のInboxItemへ保存して後から変換する工程は設けない。URLとOCRは独立した登録方式ではなく、同じ画面内でタイトルと画像を埋める入力補助とする。URLから取得したタイトルは候補として表示する。カメラ/写真のOCRは先頭行を使わず、認識行の文字領域の高さ・面積・認識確度を基に、大きく目立つ文字をタイトル候補として順位付けする。1位が十分に目立ち、同じ領域の文字認識にも曖昧さがない場合だけ候補表示し、利用者が`タイトルに使う`を選んだ時だけ反映する。確定できない場合は自動候補を出さず、目立つ領域のVision上位候補とOCR全行を提示して利用者に選ばせる。OCR全文は選択・コピー可能な確認欄へ残し、対象の`読み取りメモ`へ保存する。OCRに使った画像は対象のアイキャッチ候補にする。後から同じ対象へPlanまたはVisitを追加し、その時点で状態を通常へ移す。

クイック登録後も対象詳細の`対象情報・画像を編集`からアイキャッチを差し替え・解除できる。画像は読み込み時に長辺1600px以内、JPEG品質85%へ圧縮し、元画像のメタデータを保持しない。

登録フロー:

1. `体験済みを記録`を選択
2. コンパクトなジャンルメニューでジャンルを選択。全ジャンル一覧を常時展開しない
3. 主操作の「新しい作品・対象を登録」、または補助操作の「登録済み作品・対象に記録を追加」を選択
4. 既存対象の場合は検索結果から対象を選び、対象側情報を参照して今回固有のVisitだけを入力
5. 新規対象の場合は対象名だけで作成可能とし、必要に応じてシリーズを検索・連結
6. 記録の必須情報を入力
7. 必要な補助ユニットだけ展開
8. 保存後に記録詳細を開く

下部の`追加`タブの`体験済みを記録`では、ジャンルをコンパクトなメニューで選んだあと、主操作の`新しい作品・対象を登録`と、補助操作の`登録済み作品・対象に記録を追加`を同じ選択画面に表示する。既存対象は選択ジャンル内をタイトルまたはシリーズ名で検索でき、未入力時は最近更新した対象を少数だけ表示する。

登録済み対象の候補部分は画面全体とは別の縦スクロール領域にし、候補が増えても下部説明や閉じる操作へ到達できる高さに制限する。右端にはスクロールインジケータを表示する。

予定詳細の`参加記録を入力`はVisitを即時作成せず、同じ記録入力フォームを開く。対象、予定日時、終了日時、会場、座席、金額、メモ、公式URL/購入URLを初期値として引き継ぎ、利用者が確認・修正して保存した時だけVisitを作成する。保存成功と同じ処理内でPlanを参加済みにし、代表のTicketAttemptも参加済みに更新する。入力をキャンセルした場合はPlanとTicketAttemptを変更しない。

入口の情報優先順位:

```text
ジャンル [観劇 ▼]

[ ＋ 新しい作品・対象を登録 ]

または

登録済み作品・対象に記録を追加
[ タイトルを検索 ]
```

「既存対象への記録追加」と「シリーズ連結」は別機能とする。既存対象への追加は再鑑賞、再訪、再読、同じ銘柄の再記録に使う。シリーズ連結は新しい対象を別作品として作成したうえで任意の親シリーズへ紐付ける。

既存対象を選んだ場合に参照する対象側情報:

- タイトル、ジャンル、シリーズ、代表写真
- 基本の人物・団体、公式URL、対象種別

Visitへ入力する今回固有の情報:

- 体験日、会場、当日の人物・団体
- 写真、評価、座席、金額、感想、天気

対象情報をVisitへ無条件コピーせず、対象はリレーション参照、当日固有情報はVisitのスナップショットとして保存する。

常時表示:

- ジャンル
- 対象名
- 日付
- 場所
- 評価または状態
- メモ

アコーディオン:

- 人物・団体
- 写真
- チケット・座席
- OCR・取込
- 金額
- 公式情報
- 詳細オプション

新規対象を作る場合でも、対象側の詳細情報をすべて同時入力させない。まず名称だけで対象を作成でき、対象詳細から後で補完できる。

## 10. 編集画面

編集画面は次の3種類へ分離する。

### 対象を編集

- 対象名
- シリーズ、サブ種別
- 代表写真
- 基本となる人物・団体
- 公式情報
- 対象メモ

### 記録を編集

- 日付、場所
- 評価、状態
- 当日の人物・団体
- 写真、OCR
- 座席、金額、天気
- 感想、詳細オプション

対象名や対象の公式情報を変更しない。

### 予定・チケットを編集

- 開催日時、開場、会場
- 会場名は手入力でき、Apple Maps選択は同じ予定の会場名・住所・座標を補完する
- 予定固有の公式ページは`この予定の公式URL`と明示し、申込・購入URLと区別する
- 抽選または発売・予約のスケジュール
- 取得後のチケットメモ、リンク、任意のQR・画像
- 発券・表示確認と任意の確認リマインダー
- 予定メモ

公演名、サブタイトル、会場、住所、予定公式URLは入力後も項目名が残る明示ラベルを使う。Planだけを編集する時は申込タグを表示しないため、自由記述欄を`予定メモ`と表記する。体験済みの感想や写真を変更しない。参加後はPlanからVisit作成へ遷移する。

## 11. 御朱印専用登録フロー

御朱印は一般的な対象選択より先に、登録先の御朱印帳を選ぶ。

```text
御朱印を登録
↓
使用中の御朱印帳を選択
↓
新しい寺社 / 登録済み寺社を選択
↓
御朱印を入力
↓
保存して完了 / 保存して同じ寺社で続けて登録
```

御朱印帳選択画面:

- 使用中の御朱印帳を表紙画像、名称、登録済み御朱印件数で表示
- 同じ利用者が寺社や用途ごとに複数冊を並行利用できる
- `新しい御朱印帳を登録`を補助操作として同じ画面へ置く
- 閉じた御朱印帳は新規追加候補に出さないが、過去帳一覧から閲覧・編集できる

御朱印帳の管理:

- ページ数、総ページ容量、使用ページ数を管理しない
- 裏面利用、見開き、書置きなどの差を自動判定しない
- 満了の自動判定、自動クローズを行わない
- 利用者の明示操作だけで御朱印帳を閉じる
- 閉じた御朱印帳は新規御朱印を追加できないが、既存御朱印と帳面情報は編集できる
- 御朱印帳には登録済み御朱印の件数を表示する

寺社選択:

```text
[ ＋ 新しい寺社の御朱印を登録 ]

または

登録済み寺社から選ぶ
[ 寺社名を検索 ]
```

御朱印登録項目:

- 御朱印画像/アイキャッチ: 任意
- 寺社名: 必須
- よみ: PlaceMasterの読みを寺社名上部へ薄いルビとして表示
- 住所、ミニMap、公式URL、御祭神: 任意。登録済み寺社から引継可能
- 参拝・拝受日時、写真、同行者、メモ: 任意
- 御朱印名/種類、通常/限定、直書き/書置き: 任意
- 初穂料・納経料: 任意。`300円 / 500円 / その他`をクイック選択し、その他は任意金額を入力

保存操作:

- `保存して完了`
- `保存して同じ寺社で続けて登録`

続けて登録では御朱印帳、寺社、日時、同行者を保持する。御朱印画像、御朱印名/種類、金額、写真、メモは次の記録へ引き継がない。

御朱印帳の基本情報:

- 表紙画像
- 御朱印帳名、または購入した寺社
- `神社用 / お寺用 / 共用`
- 使い始めた日
- メモ

御朱印帳は長押しから編集、閉じる/再開、削除へ進める。削除は帳面内の御朱印と写真を含むため、対象件数表示、バックアップ案内、`削除する`の確認入力を含む3段階確認にする。削除しても寺社マスターと別の御朱印帳は削除しない。

## 12. 共通入力ルール

### OCR・URL取込

OCRとURL取込は保存操作ではなく入力補助とする。

1. 画像、URL、貼り付けテキストを読み取る
2. タイトル、日付、会場、人物、金額、ISBNなどの反映先を候補表示する
3. 利用者が候補ごとに反映先変更、編集、除外を行う
4. `反映する`を押した項目だけフォームへ入れる

- 信頼度が低い候補は要確認表示にする
- 既存入力を自動上書きしない
- OCR全文を確認画面へ残し、選択、コピー、貼り直しを可能にする
- 公演系は登録画面上部に`公式サイトから情報を取得`と`チラシ・チケットをOCRで読み取る`を常設する
- 本はISBNバーコードを優先し、奥付OCRを予備経路にする。ISBNは任意の内部識別情報として保持し、通常入力で手入力を要求しない

### 人物・団体の重複候補

人物名の検索用文字列は、Unicode正規化後に半角/全角スペース、連続空白、改行、タブを除去し、英字の大文字/小文字を無視する。

```text
山田 太郎
山田　太郎
山田太郎
```

上記は同一候補として提示する。さらに表示名・よみ・別名のいずれからでも検索できるようにし、人物の検索・登録画面では汎用の入力補助設定にかかわらず候補を常時表示する。候補選択または完全一致入力では既存人物を再利用し、部分一致や同姓同名は候補から利用者が判断する。この規則は人物マスター管理、FAVO、著者、俳優、アーティスト、監督、作家などPersonMasterを使う全ジャンルへ適用する。

### SNSタグ

全ジャンルの対象と記録に、複数登録可能な任意のSNSタグを持たせる。

- `#`なしの入力は表示時に補完する
- 全角/半角スペースを無視して重複候補を出す
- URL/OCRから公式タグ候補を提案する
- タグ群をまとめてコピーできる
- 通常は`公式情報`アコーディオン内へ置く

### 日付

期間は終了日を必須にしない。開始日だけで保存でき、終了日がない対象を無期限の`開催中`とは自動判定しない。

### 写真と写真に紐づく情報

写真を用途別に二重保存しない。共通写真へ任意の作品情報または体験情報を付け、詳細画面で意味のあるまとまりとして再構成する。

- 美術展: 作品名、作家名、メモ
- おでかけ: 名前、種類、メモ、任意の金額
- 写真がない場合はテキストだけの作品/体験メモを追加できる
- 情報付き写真も通常の写真ギャラリーへ含める

### 評価

映画と本は、記録回ごとに`1.0...5.0`を0.5刻みで評価できる。ジャンルごとに機能ON/OFF可能、初期値はOFF、未評価保存を許可する。OFFにしても保存済み評価は削除しない。一覧への評価表示は別設定とする。

## 13. ジャンル別登録フロー

### 映画

```text
映画を記録
├ 新しい映画を登録
└ 登録済み映画に鑑賞記録を追加 [検索]
```

映画情報:

- タイトル必須
- 読み、原題、ポスター、公開年、監督、出演者、制作会社、公式URLは任意
- 1作品は複数のコレクションへ所属できる
- コレクションは代表画像、作品数、作品一覧、公開順/時系列/任意順を持つ

鑑賞記録:

- 鑑賞予定/鑑賞済み、鑑賞日、映画館、上映形式、同行者、写真/半券/OCR、金額、感想/メモ、任意評価
- 再鑑賞は映画情報を参照し、新しい鑑賞記録だけを追加する

映画トップはコレクションカードを横スクロール表示し、`一覧を表示`からコレクション一覧へ進む。主要都市のシネコンとミニシアターをPlaceMasterの初期候補へ収録する。

### 観劇

通常利用は`公演 -> 観劇回`の2層とし、作品/演目の理解を登録時に要求しない。再演をまとめる機能は内部拡張余地を残し、必要な利用者だけ後から使えるようにする。

公演情報:

- 公演名必須
- メイン画像/チラシ、公演種別、劇団/主催、公式URLは任意
- 人物・団体は閉じたアコーディオンに置き、原作/原案、作/脚本、演出、出演者、音楽、振付などを役割付きで複数登録できる
- 公演名と主催が近い既存公演がある場合は、情報を引き継ぐか新規作成するか確認する。自動統合しない
- チラシ/ポスターは公演、当日の写真/半券は観劇回へ保存する

観劇回:

- 観劇日時、会場、座席自由入力、当日の出演者差分、写真/半券、金額、同行者、感想/メモ
- 開場時刻は予定/チケット側、上演時間は公演側の任意項目、休憩は標準項目にしない
- 感情タグ初期候補は`また観たい / 泣いた / 笑った / 驚いた / 圧倒された / 考えさせられた / 音楽が好き / 演出が好き / 衣装・美術が好き`

公演種別初期候補:

- 演劇、2.5次元舞台、ミュージカル、歌舞伎、落語・寄席、ダンス・バレエ、オペラ、その他
- 2.5次元舞台は観劇の独立した公演種別とし、演劇・ミュージカルのどちらかへ強制的に寄せない
- コンサート／ライブは別のLIVEテンプレで扱い、アイスショー、マジック、サーカス、能、狂言、講談、浪曲、朗読劇等は`その他`から具体名を入力する
- `その他`を選んだ場合は`その他`という文字を保存せず、入力した具体名を表示・検索・統計に使う。固定候補は安定キー、具体名は後方互換JSONに保持する
- 公演種別は公演である`ExperienceEvent.subTypeKey`、鑑賞方法は観劇回である`Visit.unitFieldsRaw.styleNames`に分離する。鑑賞方法の初期候補は`現地 / 配信 / ライブビューイング`
- 将来カスタム候補の追加・並べ替え・非表示・統合を実装する場合も、使用済みの安定キーと具体名を破壊しない

一覧サマリーはチラシ、公演名、観劇日、劇場、予定/観劇済みに限定する。

### ライブ

通常利用は`ライブ・イベント -> 参加回`の2層とし、入口はアーティストではなくライブ名から始める。

```text
ライブを記録
├ 新しいライブを登録
└ 登録済みライブに参加記録を追加 [検索]
```

ライブ情報:

- ライブ名必須
- 種別は`ワンマン / 対バン / フェスティバル / ライブイベント / 配信ライブ / その他`
- アーティストは最初から表示して複数登録可能。役割は`メイン / 出演 / ゲスト / オープニングアクト`を任意設定する
- ツアーは種別にせず、必要な場合だけ関連ライブとして後からまとめる

参加回:

- 参加日時、会場、写真/アイキャッチ、感想/メモを基本とする
- 座席/整理番号、当日のゲスト、セットリスト、同行者、金額、公式情報は閉じた任意項目
- セットリストは曲名と順番を持ち、まとめて貼り付け可能。アンコールは区切りで表現する
- フェスは出演者全員と実際に観たアーティストを分け、詳細ON時だけアーティスト別セットリスト、ステージ、時間帯を記録する
- 配信ライブは会場の代わりに配信サービスと視聴URLを使う
- 感情タグ初期候補は`また行きたい / 泣いた / 笑った / 驚いた / 圧倒された / 盛り上がった / 音が良かった / 演出が好き / セットリストが好き`

ライブトップは今後のライブ、アーティスト、参加したライブ、データがある場合だけツアー/関連ライブを表示する。

### 本

通常利用は`本 -> 読書記録`の2層とする。

```text
本を記録
├ 新しい本を登録
└ 登録済みの本に読書記録を追加 [タイトル・著者検索]
```

読書記録の新規登録・編集・登録済み本への追加は、次の順で統一する。

1. `アイキャッチ`（本の表紙と別管理。未設定時は表紙を表示）
2. `本の情報`（初期は閉じる）
3. `読書の記録`（初期は閉じる）
4. `写真`（初期は開く）
5. `読書メモ`（初期は開く）

`本の情報`は書名必須、シリーズ・巻数・著者、本の種類、公式URLに絞る。詳細な書誌情報はISBN等から自動取得できる土台ができるまで入力させない。`読書の記録`は開始日、任意の終了日、任意評価だけとし、開始・終了は1つのカレンダーで最大2日を選ぶ。開始日だけでも保存可能とする。読書状態、紙／電子／オーディオ、引用、印象タグ、人物、OCR、金額、保管場所、貸出状況、読書タイマー、ページ進捗は現行フォームへ入れない。

日程を持たない`本を登録する`では、シリーズ名・巻数・著者を独立保存し、表示先として`気になる / 積読`だけを選ぶ。これは読書回フォームの詳細な状態管理ではない。シリーズ巻一覧の`次の巻を追加`は、シリーズ名・著者・本の種類と既存最大巻数+1を初期入力し、積読を初期状態にする。数値の巻がないシリーズは巻数を空欄にして利用者が入力する。ISBNは専用項目の保存先ができるまで表示しない。

詳細画面はHeroの後も同じ`本の情報 / 読書の記録 / 写真 / 読書メモ`へ揃える。初期開閉状態もフォームと同じにし、書籍では会場、地図、チケット、費用、人物等の汎用Sectionを表示しない。再読は同じ本へ新しい読書記録を追加して表現する。

### 美術展・展示会

通常利用は`展覧会 -> 鑑賞記録`の2層とする。同じ巡回展は展覧会を共通化し、会場と鑑賞日は鑑賞記録へ持たせる。会場ごとに内容やタイトルが大きく違う場合だけ別展覧会として関連付ける。

展覧会情報:

- 展覧会名必須
- メイン画像/チラシ、開催開始日、任意の終了日、作家/アーティスト、主催/企画、公式URL、SNSタグ
- 排他的な単一種別を使わず、`現代美術 / 絵画 / 彫刻 / 写真 / 映像 / インスタレーション / メディアアート / 建築 / デザイン / 工芸 / ファッション / 漫画・アニメ / 歴史・文化 / 科学・自然`などを複数選択できるジャンル・テーマとして扱う

鑑賞記録:

- 鑑賞日、会場、写真、同行者、金額、感想/メモ、印象タグ
- 写真へ作品名、作家名、メモを付けると`印象に残った作品`として自動表示する
- 写真がない作品はテキストだけで記録できる
- 印象タグ初期候補は`また行きたい / 心に残った / 驚いた / 圧倒された / 考えさせられた / 展示空間が好き / 作品構成が好き`

展覧会トップは開催中/これから行きたい展覧会、チケットスケジュール最大2行、最近観た展覧会、アーティスト、美術館/ギャラリー、写真ギャラリーを表示する。

### おでかけ施設

```text
おでかけを記録
↓
テーマパーク / 動物園 / 水族館 / 植物園 / その他
↓
お気に入り、最近使った施設、全施設から選択 / 新しい施設を登録
↓
訪問記録を入力
```

施設情報は施設名必須、種別、メイン画像、読み、住所/Map、公式URL、SNSタグ、お気に入りを持つ。訪問記録は訪問日、写真/アイキャッチ、同行者、チケット/予約、金額、天気、体験、感想/メモ、SNSタグを持つ。

体験情報:

- 共通写真へ体験名、種類、メモ、任意金額を付ける。写真なしでも登録可能
- テーマパークの初期候補は`アトラクション / ショー・パレード / グリーティング / イベント / フード・ドリンク / グッズ・購入品 / その他`
- 動物園、水族館、植物園では表示候補を動物、生き物、植物、季節展示、餌やり/体験などへ変える
- 体験種類はカスタム追加、並び替え、非表示、統合可能

おでかけトップはこれからのおでかけ、チケットスケジュール最大2行、お気に入り施設、最近行った施設、写真ギャラリーを表示する。

### お酒

```text
お酒を記録
├ 新しいお酒を登録
└ 登録済みのお酒に飲酒記録を追加 [検索]
```

- 初期種別は日本酒、ワイン、ビール、ウイスキー、焼酎、その他
- 既存対象は種別、銘柄、メーカー/蔵、産地、ラベル、仕様、公式URLを参照する
- 飲酒記録は日付、場所、写真、飲み方、金額、同行者、感想/メモを持つ
- 軽い印象は`また飲みたい / 好み / ふつう / 合わなかった`の単一選択、未選択可
- 香り、甘辛、軽重、酸味、余韻、飲みやすさ等の詳細評価は機能ON時だけ表示し、酒種別でラベルを変える

## 14. チケット共通フロー

チケット登録の入口は次の3択とする。

```text
チケットを登録
├ 抽選に申し込む
├ 発売を待つ
└ チケットを取得済み
```

抽選・発売共通:

- `申込アカウント（任意）`は設定済みFC・プレイガイド等を`サービス名｜名義`で表示し、選択すると購入先・名義・登録URLを自動入力する
- 同じFCの複数名義は1名義1アカウントとして別候補にし、名義未設定とアカウント未選択も許容する
- 別アカウントへ変更した場合は関連値を新しいアカウントへ更新する。`未設定`へ戻した場合は直前のアカウントから自動入力されたままの値だけを解除し、利用者が書き換えた値は保持する
- アカウント未選択時は購入先・名義・URLを手入力できる

抽選:

- `申込枠`は`FC先行 / 公式先行 / プレイガイド先行 / カード枠 / 一般抽選 / その他`
- 申込開始、申込締切、当落発表、入金期限、発券開始、発券/受取期限を、分かる項目だけ登録する
- 申込URLからプレイガイドを自動候補にし、URLがない場合だけプレイガイドの一般入口を利用できる

発売:

- `販売方法`は`先行販売（先着） / 一般発売 / リセール / その他`
- 発売開始、申込アカウント、名義、購入先、申込・購入URLを表示する
- 同じ公演の先行販売と一般発売は別々のTicketAttemptとして登録でき、それぞれ発売アラートを持つ

取得済み:

- 購入先、金額、枚数、座席、タグ・メモを表示する
- 申込枠・販売方法・名義は表示しないが、抽選から継続した既存値は削除しない
- `購入先`はプレイガイドに限定せず、FC・公式サイト・その他の購入サイトを手入力できる
- 画像/PDF、発券・表示確認、確認リマインダーは任意
- `チケットQR・画像`は通常写真と分け、年間まとめ、写真ギャラリー、共有画像へ出さない
- QR全画面表示中は明るさと自動ロックを入場確認向けに調整する
- 動的QRやスクリーンショット無効の場合があるため、公式サイト/アプリ表示を優先する注意を出す

開催日時と会場は公演/展覧会/予定側を参照し、チケットへ重複保存しない。ジャンルトップのチケットスケジュールは共通チケットデータから直近1〜2件を表示し、登録がなければセクションごと隠す。

## 15. 場所・種別・タグのマスターUI

会場入力は利用者へ施設/ホールの階層選択を要求せず、1つの検索/自由入力欄にする。

```text
会場 [東京芸術劇場 コンサートホール]
```

- 施設名だけでも、ホール名込みでも保存可能
- 住所がある場合は名称検索ではなく住所を優先してMap表示する
- 主要都市圏の映画館、劇場/ホール、美術館/博物館/ギャラリー、おでかけ施設を初期候補として収録する
- 内部で親施設を共有しても、通常登録では細かな施設階層を見せない
- 場所マスターは`未設定 / 営業中 / 閉館・閉園`の営業状態を持つ。管理一覧では赤い閉館バッジと状態フィルター、編集では状態選択を提供する
- 閉館施設はFAVOと過去記録の登録済み場所候補で`閉館`を明示した上で利用できるが、未来予定の通常候補からは除外する

カスタム種別と印象タグは、名前、アイコン、色、並び順、表示/非表示を管理できる。未使用のカスタム項目は削除可能、使用済み項目は削除せず別項目へ統合または非表示にする。初期項目は削除せず非表示のみ可能とする。

## 16. 実装移行方針

1. 既存モデルは維持し、まずViewの責務を分離する。
2. `EditExperienceView`が同時更新しているExperienceEvent/Visitを、対象編集と記録編集へ分割する。観劇は分割済み。ほかのテンプレートは観劇の完成後に共通完成条件を抽出して適用する。
3. `AddExperienceView`の先頭に既存対象検索を追加し、新規対象作成と既存対象へのVisit追加を同じ入口から選べるようにする。
4. `CategoryTopView`は対象ライブラリを主役に再構成する。
5. `ExperienceDetailView`と`EventDetailView`を閲覧専用として整理する。
6. View分割後にデザインラフを各画面へ適用する。

## 17. 完成条件

- どの情報がExperienceEvent、Visit、Plan、TicketAttemptのどれに属するか画面上で判断できる
- 一覧から編集コントロールが排除されている
- 対象編集で過去Visitの固有情報が変わらない
- 記録編集で対象名や対象公式情報が意図せず変わらない
- Plan編集とVisit編集が混在しない
- 登録は必須情報だけで保存でき、詳細入力は任意展開できる

## 18. 設定の情報設計

設定トップは、製品版では`個人情報 / 記録・アプリ管理 / サービス・情報`の3区分、DEBUG版では末尾の`開発用`を加えた4区分とする。各行には設定できる内容を短いマイクロテキストで表示する。ジャンルは表示順、色、記録項目まで扱う中核設定のため、`アプリ設定`内へ入れずトップから直接開く。

設定と入力フォームの説明は重要度を分ける。行の内容を短く列挙するだけなら11pt Regularのマイクロコピーを使う。選択の影響、未入力時の挙動、次に登録すべき内容など、利用者が理解してから操作する必要がある場合は、`情報アイコン / 10.5pt Semiboldの短い見出し / 11pt Regularの1〜2行説明`を持つ淡いテーマ色の情報枠で明示する。本文や入力値と同じ16ptへ大きくせず、同じ説明をSection見出しやfooterへ重複させない。観劇の申込方法にある`この登録で入力する項目`を基準表現とする。

各設定画面は観劇詳細登録と同様に、Section名をカード外へ明示し、カード内の項目は54pt以上の行高と視認できる区切り線で分ける。設定名を16pt Semibold、補足を11pt Regularとして、設定名・現在値・操作部品の優先順位を崩さない。破壊的操作や保存データへ波及する変更は、通常項目とは別Sectionに分離する。

```text
設定
├ 個人情報
│  └ プロフィール・連携
│     ├ プロフィール・SNS
│     └ チケット・会員・カレンダー
├ 記録・アプリ管理
│  ├ ジャンル設定
│  ├ マスターデータ
│  ├ アプリ設定
│  │  ├ 表示・外観
│  │  ├ 記録・入力補助
│  │  └ 通知
│  └ データと同期
│     ├ データ管理
│     └ 同期・バックアップ
├ サービス・情報
│  ├ プラン
│  └ サポート
└ 開発用（DEBUGのみ）
   └ 開発者メニュー
```

`プロフィール・SNS`は左にプロフィール写真、右に表示名入力と写真操作を置く。プロフィールとSNSは他の利用者とつながるための公開機能ではなく、入力内容を運営者へ送信・収集しない。SNS発信時に登録アカウントをすぐ開くショートカット用途であることを、10.5pt見出し＋11pt本文の情報枠で明示する。

`チケット・会員・カレンダー`は、FC・プレイガイド・劇場会員・カード枠の情報と、外部カレンダー表示設定を扱う。`登録情報`だけの曖昧な名称は使わず、設定対象を画面名と追加操作へ明示する。チケット・会員情報のサービス名へ2文字以上入力すると、チケット登録でも共用するプレイガイド正本から正式名称・別名・URLで最大5件を検索し、入力欄直下へ`正式名称 / 区分 / 公式URL`を表示する。候補選択ではサービス名、種別`プレイガイド`、サイトURLを同時反映し、候補とキーボードを閉じる。候補外は手入力を維持し、文字入力だけで自動確定・自動上書きしない。

同画面の`チケット・会員情報を追加`は、既存項目を開く通常行と混同しない全幅44pt以上のテーマ色塗りボタンにする。設定内の淡色情報枠は12ptの連続角丸とし、外側の白いSectionカードと角の印象を揃える。

トップと「アプリ設定」のマイクロテキストは次を正本とする。

- ジャンル設定: 表示順、表示・非表示、色、記録項目
- 表示・外観: Home表示、外観、文字、フォント、テーマ
- 記録・入力補助: 初期値、写真圧縮、URL・OCR・Map・天気の補助
- 通知: チケット期限、公演前日・当日、会員期限、レポート

組み込みジャンルの詳細設定は、テーマカラー、使用する記録項目、SNS、表示・非表示だけを利用者設定とする。表示名、アイコン、テンプレタイプ、各項目名は標準仕様として固定し、変更したい場合は`自作ジャンルとして複製`へ誘導する。記録項目は汎用ユニット名を全ジャンルへ一律表示せず、現在の登録画面に合わせる。書籍は`本の情報 / 読書の記録 / 写真 / 読書メモ`、Goodsはシリーズ・ラインナップ・入手／手放しを専用構造として固定表示する。観劇は`参加日・会場 / 評価 / 感想・感情タグ`を固定し、`鑑賞記録 / 写真・アイキャッチ / 集計記録 / 読み取り情報 / 公演公式情報`だけ変更可能にする。テーマカラーは実際の色見本と名称が一致する専用一覧から選ぶ。`標準設定に戻す`は色と記録項目だけを初期値へ戻し、記録、SNS、表示状態は変更しない。自作ジャンルでは表示名と各項目名へ値入力後も消えない見出しを置き、アイコンは内部識別子の直接入力ではなくプレビュー付き候補から選択する。

初回ジャンル選択のやり直しは「設定 > ジャンル設定」の末尾に置き、既存記録を削除しないことを明記する。テスト権利、仮データ、通知診断、全データ削除テストはDEBUGビルドだけの独立した「開発用 > 開発者メニュー」へ分離し、通常利用者へ表示しない。

「記録・入力補助」には現在動作する設定だけを置く。記録日は今日を初期値として入力画面で変更できるため、単一選択肢の設定は置かない。写真設定は`写真追加の優先方法`として写真ライブラリ／カメラを選び、未設定時は写真ライブラリを主要ボタンにする。もう一方の追加方法も補助ボタンとして常に残す。Apple Musicなど未実装の将来候補も通常設定へ予告表示しない。

「表示・外観」のHome表示には、現在内容を表示できるセクションだけを置く。`Ticket Schedule`はHomeの英字見出しと同じ表記にする。上部ジャンルナビゲーションは固定表示のため`ジャンル一覧`設定を置かない。写真付き記録の横スクロールは「最近の思い出」と呼ぶ。お気に入り/ベストは集計元が実装されるまでHomeにも設定にも予告枠を出さない。

通知設定の`FC・会員期限`には、アカウント側で有効期限と期限通知を設定した場合に、30日前・7日前・当日9時へサービス名付きで通知することを情報枠で明示する。期間の振り返りは`月刊・年間Favoreco`へ一本化し、前月／前年の記録・写真・ジャンル傾向からレポートを自動提案する。通知タップ後は期間集計の責務を持つ統計タブの該当レポートへ直接進む。Homeは現在性の高い情報、FAVOは人物・作品・場所等の好きな対象からの振り返りに保ち、期間まとめの保存先・主導線にはしない。通知処理が未接続の`思い出リマインダー`Toggleは通常設定へ表示しない。

## FAVOプロフィール編集とHero

MY FAVO編集は、人物・団体／キャスト、作品／体験、場所の3群を同じ検索画面で提示する。人物は登録済みマスターから選ぶほか、新規登録で人物マスター・FAVOプロフィール・MY FAVO固定を一度に作る。固定済み行のタップとFAVO詳細右上の鉛筆からプロフィール編集へ進む。

編集Formは次の責務を分ける。

- `基本情報・全体へ反映`: 正式名、よみ／シリーズ／都道府県、役割／住所、公式URL。保存するとマスター管理、キャスト、候補表示に反映する
- `FAVOでの表示`: 呼び名、FAVOカラー、推し始めた日、きっかけ、個人メモ。対象のFAVO詳細だけに反映する
- `FAVO写真`: 16:9のHero写真1枚と正方形アイコン1枚。写真選択中はDraftへ保持し、保存時だけモデルへ反映する

FAVO詳細HeroはFAVO専用Hero写真を最優先し、未設定なら人物マスター画像または作品アイキャッチ、それもなければFAVO色グラデーションを表示する。アイコンはFAVO専用、マスター画像、種別アイコンの順で戻る。

Heroと次の予定の後へ`推しギャラリー`を置き、3列で最大6枚を先行表示する。写真詳細は全プランで閲覧可能とする。Pro／Premiumは一度に20枚まで追加でき、保存時に長辺1600px以内へ縮小する。管理画面では任意の日付・メモ、プロフィールごとに1枚のお気に入り、ドラッグ並べ替え、削除を提供する。無料プランへ戻った場合も保存済み写真は隠さず、追加・編集・並べ替え・削除だけをロックする。

Heroと次の予定の後、推しギャラリーの前へ`記念日`を置く。人物・作品／体験・場所の全種別で、名称と起点日を複数登録できる。詳細は次回が近い順に3件まで表示し、起点日、次回の月日、残り日数、1年以上経過している場合の周年を示す。管理画面では追加、編集、ドラッグ並べ替え、確認付き削除を提供する。記念日は全プラン共通とし、通知は保存基盤とは分けて後続実装する。2月29日は2月28日や3月1日へ暗黙補正せず、次の閏年を次回とする。

### 観劇公演の同一性とアイキャッチ

同一ジャンルの同名公演は、新規記録・公演登録・予定登録で既存公演マスターを再利用する。空白・全半角・大文字小文字だけが異なる保存済み公演もProductionsでは1作品として扱い、予定・申込を持たない純粋な興味あり公演はInterestsだけへ表示してProductionsへ二重表示しない。公演登録で選んだアイキャッチはB判比率へ中央トリミングして保存し、一覧は保存済みアイキャッチまたは代表写真を固定枠の中央aspect fillで表示する。

### 観劇の登録系フォーム

公演登録、公演情報編集、公演地編集、観劇予定、チケット手配、観劇記録追加・編集の通常入力は、上段16ptの項目名と下段16ptの入力欄を持つ66pt基準行へ統一する。項目名と上枠・区切り線の間に9pt、行下に8ptを確保する。`任意 / 必須`は項目名の隣、プレースホルダーは下段へ置く。通常の文字入力は値がある時だけ右端へ×丸を表示し、その項目を全文消去できる。タグ入力は例外として、改行確定ごとに折り返しカプセルへ変換し、各カプセル内の×で個別削除する。一括削除×は置かない。プルダウンの選択値は16ptで右寄せし、右端から4pt追加で離す。メモは5行分、座席は通常1行・長文時のみ最大2行とする。公演登録と公演情報編集の`公演基本情報`は初期展開し、`会期・会場`と同じカード見出しと標準矢印で開閉できる。観劇記録では公演名・シリーズ、日付・時刻・鑑賞方法・会場・住所・評価、チケット状態・座席、金額、感想メモ、公式URL・SNS、OCR原文、人物名、自由感情タグも同じ構成にし、写真・人物候補・感情タグ候補のカード/グリッドは既存構造を維持する。

公演種別は未選択時も`未設定`を表示し、下段全体を選択Menuのタップ範囲とする。SNSは共通16pt項目名と上下6pt余白を使い、各サービスを28ptアイコンと`X / Instagram / Threads`の英字名を併記したカプセルで示す。公演地の会場名は2文字以上の入力を450ms待ってApple Maps候補を最大3件表示し、候補選択で会場名と住所を同時反映する。会場名と住所が揃った時は会期入力の下へ170pt高のMapプレビューを表示し、会場名と住所を組み合わせて位置を解決する。

共通セクション名は16pt Semibold、通常項目名は16pt Semibold・`primary 78%`とする。入力本文は16ptを基準にし、住所とURLだけは長文を見通しやすくするため入力値・プレースホルダーを14ptとする。Apple Maps候補は会場名の完全一致、前方一致、部分一致の順で表示し、文字一致する候補がある時は関連施設だけの候補を混ぜない。

公演地名、会場、住所、会期、開始日、終了日の項目名はすべて16pt Semibold、自由入力値とプレースホルダーは16pt Regularへ揃える。compact DatePickerだけは標準17pt相当から15pt相当へ縮小する。

観劇予定追加・編集の`体験日程`では、共通日付と`開場 / 開演 / 終了`を別行にする。日付行の右端に×を置き、解除時は開場・開演・終了を隠して日付行を`日時未定 / 日付を設定`へ切り替える。日時未定でも予定を保存できる。日付と各時刻は二段構成の下段右へ置き、この4行だけはボタン上の空きを詰め、下の罫線との間隔を確保した62pt基準行とする。時刻は`00:00〜23:50`を`HH:mm`の1項目として並べる単一列ホイールで10分刻みに選び、時と分を別列にはしない。新規の公演・イベント名は項目行全体をタップすると入力へフォーカスする。予定対象の選択済み公演タイトルは13pt Semibold、`Apple Mapsで会場・住所を入力`は13pt Semiboldの1行とし、狭幅時だけ78%まで縮小する。

### 観劇公演登録の共通入力フォーム

保存後はフォーム末尾の保存カードを同じ位置で次操作カードへ置き換える。見出し`公演を保存しました`は1行固定とし、`観劇予定を追加 / チケットを手配 / 完了`を近接配置する。画面中央へ標準確認ダイアログを出さない。

### 2026-08-06 施設系ジャンルの場所マスター導線（最新優先）

- テーマパークは`行く予定を立てる / 施設を登録`、自然・生き物は`行く予定を立てる / スポットを登録`とする。登録は補助操作として弱い外観を使う
- `施設を登録 / スポットを登録`は自由入力のクイック登録へ進まず、全国場所カタログを入口ジャンルの施設種別へ絞って開く。テーマパークはテーマパーク・遊園地、自然・生き物は動物園・水族館・植物園・公園・自然公園等を対象とする
- 全国場所カタログの分類キーはすべて日本語へ変換し、未知のキーも英語のまま露出させない。絞り込み名は全体=`場所種別`、ミュージアム／テーマパーク=`施設種別`、自然・生き物=`スポット種別`とする。各行は公式サイト、情報元、確認日を登録前に表示し、2つのURLをタップして外部サイトで確認できる。取込操作は保存先を明示した`場所マスターに追加`とし、一度登録した行は`登録済み`で無効化する。利用者は保存したい場所だけを一度登録し、訪問のたびに再操作しない
- 公演・予定の公式URLと会場・施設の公式URLは別データとして扱う。会場選択で`PlaceMaster.officialURL`を公演・予定の`officialURL`へ自動コピーしない。会場公式サイトは登録・編集フォームと予定／記録／施設詳細の施設名・住所・Map付近に、11pt Regularの控えめな外部リンクとして表示する
- カタログ行の追加は既存PlaceMasterを重複作成せず、以後の予定・記録の`登録済みの場所`候補として利用する。カタログにない場所は予定・記録の場所欄へ名称と住所を入力し、親データの保存時にPlaceMaster化する
- 予定作成では新しい対象とPlanを同時保存するか、既存ExperienceEventへ新しいPlanだけを追加する。場所欄では登録済みPlaceMasterと未取込の全国場所カタログ候補を同じ検索語から提示し、選択後に住所・座標・Mapへ反映する
- テーマパーク／自然・生き物の`施設情報`には、Plan／Visitの参照がある場所だけでなく、各ジャンルの分類タグを持つ登録済みPlaceMasterも表示する。施設情報の表示単位はPlaceMasterだけとし、未紐付けを含む旧ExperienceEventカードは表示しない。旧ExperienceEventは削除せず、気になる／予定の条件に合う場合は各Section、Visitがある場合は来園／体験記録の名称・画像として互換利用する
- 施設カードから開く施設詳細は、施設名・住所・Map・公式URL・今後の予定・来園／体験記録をまとめる。下部の`行く予定 / 来園を記録・体験を記録`は同じPlaceMasterを登録フォームへ渡し、施設名・住所・座標を初期入力する。保存したPlan／Visitも同じPlaceMasterへ紐づき、詳細の予定／履歴へ戻る
- ミュージアムは展示が複数施設・会期を持ち得るため、この単独施設詳細をジャンルトップへ置かない。登録済みPlaceMasterは展示・予定・鑑賞記録フォーム内で選択し、場所情報を再利用する

### 2026-08-07 鑑賞済みの表示単位（最新優先）

- 映像作品とミュージアムの`鑑賞済み / 鑑賞記録`はEventではなくVisitの一覧とする。件数もVisit数とし、同じ作品／展示のリピート鑑賞を日付別のカードで表示する
- カードタップは1回の鑑賞記録詳細を開く。映像作品の通常導線に作品情報ページを置かず、Eventは共通タイトル・画像等の内部データとして使う
- 映像作品を含む観劇以外の記録詳細は、本文SectionごとにSwiftUIの型境界を置く。全Sectionを単一の巨大なジェネリック型へ結合せず、実機で詳細を開く時の型メタデータ再帰クラッシュを防ぐ。見た目、Section順、保存内容は変えない
- ミュージアムは`展示Event → 鑑賞Visit`の親子関係を内部で使う。Museum LogとVisit Heroには、同じEventのVisitを鑑賞日・作成日・IDの順に並べて算出した`鑑賞n回目`を表示する。鑑賞日の編集後は回数表示も自動で並び替える
- Visit詳細の会場Map直下へ`この展示の鑑賞履歴 n回`を置き、表示中の回を明示し、別の回をタップして同じカード詳細内で切り替えられるようにする。履歴はVisit単位なのでLogにも各回がそれぞれ残る
- `この展示をもう一度記録`は同じEventへ別Visitを作る。施設名・住所・座標・展示区分・アイキャッチ・Hero背景は初期値として引き継ぐが、日時・評価・感想・通常写真・費用・人物・タグは新しい回として空にする
- `Coming Up`はジャンルを問わず見出し横に対象Plan数を表示する
- Museum Mapの下は訪問回数順のTop 10と施設別鑑賞履歴を表示する。座標のない施設は名称／住所で補完して以後も再利用する

### 2026-08-07 全ジャンル対象一覧の表示と観劇編集フィードバック

- 全ジャンルの対象一覧で該当表示を使う場合、3列ポスター／ギャラリーは初期6件・以後6件ずつ、横長は初期4件・以後4件ずつ段階表示する。全件表示後の`閉じる`は各初期件数へ戻す。2列も6件単位とする
- 公演情報編集の公演ビジュアル枠は公開公演Heroと同じ観劇金色へ揃える。ページ背景の選択中タイルは明るい金枠、右上のチェック丸、太字名称で示す
- 公演ビジュアル保存後は公演の更新日時を画像描画の更新キーとして詳細Heroを即時再読込し、一度ジャンルトップへ戻らなくても新画像を表示する
